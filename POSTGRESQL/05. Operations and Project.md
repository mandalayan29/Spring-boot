# Day 13: Programmability and Security

"Programmability" means putting logic **inside the database**: views, functions, procedures, and triggers. "Security" means controlling **who** can see and change **what**.

## Sample tables used in Day 13

Run this once. We will use these tables in many examples.

```sql
DROP TABLE IF EXISTS order_items, orders, customers, products CASCADE;

CREATE TABLE customers (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name       text NOT NULL,
  email      text NOT NULL UNIQUE,
  country    text NOT NULL DEFAULT 'IN',
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name  text NOT NULL,
  price numeric(10,2) NOT NULL CHECK (price >= 0),
  stock int NOT NULL DEFAULT 0
);

CREATE TABLE orders (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(id),
  status      text NOT NULL DEFAULT 'new',
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  id         bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id   bigint NOT NULL REFERENCES orders(id),
  product_id bigint NOT NULL REFERENCES products(id),
  quantity   int NOT NULL CHECK (quantity > 0),
  unit_price numeric(10,2) NOT NULL
);

INSERT INTO customers (name, email, country) VALUES
  ('Asha',  'asha@example.com',  'IN'),
  ('Bob',   'bob@example.com',   'US'),
  ('Chen',  'chen@example.com',  'CN');

INSERT INTO products (name, price, stock) VALUES
  ('Keyboard', 49.99, 100),
  ('Mouse',    19.99, 200),
  ('Monitor', 199.00,  50);

INSERT INTO orders (customer_id, status) VALUES (1,'paid'), (1,'new'), (2,'paid');

INSERT INTO order_items (order_id, product_id, quantity, unit_price) VALUES
  (1, 1, 1, 49.99), (1, 2, 2, 19.99),
  (2, 3, 1, 199.00),
  (3, 2, 5, 19.99);

-- Indexes on foreign keys (PostgreSQL does NOT create these for you)
CREATE INDEX ON orders (customer_id);
CREATE INDEX ON order_items (order_id);
CREATE INDEX ON order_items (product_id);
```

## 13.1 Views

### What is a view?

A **view** is a **saved query** with a name. It looks like a table, but it **stores no data**. Each time you read the view, PostgreSQL runs the saved query.

Think of it as a **window** into your tables. You can show only some columns or some rows, or hide a complex JOIN behind a simple name.

### Syntax

```sql
CREATE VIEW view_name AS
SELECT ...;

CREATE OR REPLACE VIEW view_name AS
SELECT ...;                -- change the query (you can add columns at the END only)

ALTER VIEW view_name RENAME TO new_name;
DROP VIEW view_name;
DROP VIEW IF EXISTS view_name CASCADE;   -- also drops things that depend on it
```

### Example 1: Hide a complex JOIN

```sql
CREATE VIEW order_totals AS
SELECT o.id            AS order_id,
       c.name          AS customer_name,
       o.status,
       sum(oi.quantity * oi.unit_price) AS total
FROM orders o
JOIN customers  c  ON c.id = o.customer_id
JOIN order_items oi ON oi.order_id = o.id
GROUP BY o.id, c.name, o.status;

SELECT * FROM order_totals WHERE total > 50;
```

### Example 2: Hide private columns (simple security)

```sql
CREATE VIEW customers_public AS
SELECT id, name, country           -- no email
FROM customers;
```

Now you can give a role access to `customers_public` but **not** to `customers`.

### Updatable views

A **simple** view (one table, no `GROUP BY`, no `DISTINCT`, no aggregates, no window functions) can accept `INSERT`, `UPDATE`, `DELETE`. PostgreSQL passes the change to the base table.

```sql
CREATE VIEW paid_orders AS
SELECT * FROM orders WHERE status = 'paid'
WITH CHECK OPTION;
```

`WITH CHECK OPTION` stops you from making a change that would make the row **disappear from the view**:

```sql
UPDATE paid_orders SET status = 'new' WHERE id = 1;
-- ERROR: new row violates check option for view "paid_orders"
```

Options: `WITH LOCAL CHECK OPTION` (checks only this view) or `WITH CASCADED CHECK OPTION` (default; also checks the views below it).

For complex views, use an `INSTEAD OF` trigger (see the Triggers section) to make them writable.

### View security options

```sql
-- PostgreSQL 15+: run the view with the privileges of the CALLER, not the owner
CREATE VIEW my_view WITH (security_invoker = true) AS SELECT ...;

-- Prevent leaks through cheap functions when the view is used for row hiding
CREATE VIEW my_view WITH (security_barrier = true) AS SELECT ...;
```

**Important:** By default, a view runs with the privileges of the **view owner**. That is why a view can show data from a table the user cannot read directly. With `security_invoker = true`, the user's own privileges (and row-level security) are used.

### Useful commands

```sql
\dv                          -- list views in psql
\d+ order_totals             -- show view definition
SELECT pg_get_viewdef('order_totals'::regclass, true);
```

### When to use

- You repeat the same big JOIN in many places.
- You want to give users a **limited** view of the data.
- You want a stable "interface" while the tables below change.

### When NOT to use

- Do not stack many views on top of other views. Plans become hard to read and slow.
- A view is **not faster** than the query inside it. For speed, use a materialized view or an index.

## 13.2 Materialized Views

### What is it?

A **materialized view** is a view whose **result is stored on disk**, like a real table. Reading it is fast because the work was done earlier. But the data is a **snapshot**. It becomes old until you **refresh** it.

| | View | Materialized view |
|---|---|---|
| Stores data? | No | **Yes** |
| Always fresh? | Yes | No (until refreshed) |
| Read speed | Same as the query | **Fast** |
| Can have indexes? | No | **Yes** |

### Syntax

```sql
CREATE MATERIALIZED VIEW mv_name AS
SELECT ...
[WITH [NO] DATA];            -- NO DATA = create empty; must refresh before use

REFRESH MATERIALIZED VIEW mv_name;                          -- locks readers while refreshing
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_name;             -- readers are NOT blocked

DROP MATERIALIZED VIEW mv_name;
ALTER MATERIALIZED VIEW mv_name RENAME TO new_name;
```

### Example

```sql
CREATE MATERIALIZED VIEW mv_sales_by_country AS
SELECT c.country,
       count(DISTINCT o.id)               AS orders,
       sum(oi.quantity * oi.unit_price)   AS revenue
FROM customers c
JOIN orders o       ON o.customer_id = c.id
JOIN order_items oi ON oi.order_id   = o.id
GROUP BY c.country;

SELECT * FROM mv_sales_by_country ORDER BY revenue DESC;

-- Add more orders... the materialized view does NOT change yet.
REFRESH MATERIALIZED VIEW mv_sales_by_country;     -- now it is updated
```

### Refresh without blocking readers

`CONCURRENTLY` needs a **unique index** on the materialized view (so PostgreSQL can compare old and new rows).

```sql
CREATE UNIQUE INDEX ON mv_sales_by_country (country);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_sales_by_country;
```

It is slower than a normal refresh, but users can keep reading.

### How to refresh on a schedule

PostgreSQL does **not** refresh automatically. Use one of:

- the `pg_cron` extension:
  ```sql
  SELECT cron.schedule('refresh-sales', '*/10 * * * *',
         'REFRESH MATERIALIZED VIEW CONCURRENTLY mv_sales_by_country');
  ```
- an OS `cron` job that runs `psql -c "REFRESH ..."`
- your application (for example, a Spring `@Scheduled` job)

### When to use

- Heavy reports and dashboards where "data from 10 minutes ago" is fine.
- Expensive aggregates read many times.

### When NOT to use

- You need data to be **always** live. Use a normal view or a normal query.
- The data changes a lot and refresh takes very long.

## 13.3 Functions

### What is a function?

A **function** is a saved piece of code that you call by name. It takes **inputs**, and it **returns** a value (or a table of rows). You use it inside `SELECT`, `WHERE`, and so on.

PostgreSQL supports several languages. The two you must know:

| Language | Use it for |
|---|---|
| `sql` | Simple, one-query functions. Can be inlined by the planner (fast). |
| `plpgsql` | Procedural code: variables, `IF`, loops, error handling. |

Others exist: `plpython3u`, `plperl`, and more (need extensions).

### Syntax

```sql
CREATE [OR REPLACE] FUNCTION function_name (param1 type, param2 type DEFAULT value)
RETURNS return_type
LANGUAGE sql | plpgsql
[IMMUTABLE | STABLE | VOLATILE]
[STRICT]                       -- returns NULL automatically if any input is NULL
[SECURITY INVOKER | SECURITY DEFINER]
AS $$
  ... body ...
$$;

DROP FUNCTION function_name(type, type);
```

The `$$ ... $$` is called **dollar quoting**. It lets you write quotes inside the body without escaping.

### Example 1: SQL function

```sql
CREATE OR REPLACE FUNCTION add_tax(amount numeric, rate numeric DEFAULT 0.18)
RETURNS numeric
LANGUAGE sql
IMMUTABLE
AS $$
  SELECT round(amount * (1 + rate), 2);
$$;

SELECT add_tax(100);          -- 118.00
SELECT add_tax(100, 0.05);    -- 105.00
```

### Example 2: PL/pgSQL function

```sql
CREATE OR REPLACE FUNCTION customer_order_count(p_customer_id bigint)
RETURNS int
LANGUAGE plpgsql
STABLE
AS $$
DECLARE
  v_count int;                       -- a variable
BEGIN
  SELECT count(*) INTO v_count
  FROM orders
  WHERE customer_id = p_customer_id;

  RETURN v_count;
END;
$$;

SELECT customer_order_count(1);
```

### Example 3: Return a table (many rows)

```sql
CREATE OR REPLACE FUNCTION orders_of_customer(p_customer_id bigint)
RETURNS TABLE (order_id bigint, status text, total numeric)
LANGUAGE sql
STABLE
AS $$
  SELECT o.id, o.status, sum(oi.quantity * oi.unit_price)
  FROM orders o
  JOIN order_items oi ON oi.order_id = o.id
  WHERE o.customer_id = p_customer_id
  GROUP BY o.id, o.status;
$$;

SELECT * FROM orders_of_customer(1);
```

### PL/pgSQL building blocks

```sql
CREATE OR REPLACE FUNCTION demo(p_x int)
RETURNS text
LANGUAGE plpgsql
AS $$
DECLARE
  v_result text := '';
BEGIN
  -- IF / ELSIF / ELSE
  IF p_x < 0 THEN
    v_result := 'negative';
  ELSIF p_x = 0 THEN
    v_result := 'zero';
  ELSE
    v_result := 'positive';
  END IF;

  -- FOR loop
  FOR i IN 1..3 LOOP
    v_result := v_result || ' ' || i;
  END LOOP;

  -- Loop over query rows
  -- FOR r IN SELECT id FROM customers LOOP ... END LOOP;

  -- Raise messages and errors
  RAISE NOTICE 'x is %', p_x;                 -- shows a message
  IF p_x > 1000 THEN
    RAISE EXCEPTION 'x too big: %', p_x USING ERRCODE = '22003';
  END IF;

  RETURN v_result;
EXCEPTION
  WHEN division_by_zero THEN
    RETURN 'math error';
  WHEN OTHERS THEN
    RAISE;                                    -- re-throw the same error
END;
$$;
```

Useful statements: `SELECT ... INTO var`, `FOUND` (true if the last query found rows), `GET DIAGNOSTICS n = ROW_COUNT`, `RETURN QUERY`, `RETURN NEXT`, `PERFORM` (run a query and ignore the result).

> **Note:** A block with an `EXCEPTION` part creates a **sub-transaction**. This has a small cost. Use it only when you need it.

### Volatility: IMMUTABLE, STABLE, VOLATILE

This tells the planner how "predictable" your function is. It affects speed and index use.

| Label | Meaning | Example |
|---|---|---|
| `IMMUTABLE` | Same input → **always** same output. No table reads. | `add_tax(100)` |
| `STABLE` | Same input → same output **inside one statement**. May read tables. | `customer_order_count(1)` |
| `VOLATILE` (default) | Can change anytime or has side effects. | `random()`, `nextval()`, functions that write |

- Only `IMMUTABLE` functions can be used in **expression indexes**.
- Do not lie. A wrong label gives wrong results.

### SECURITY DEFINER

- `SECURITY INVOKER` (default): runs with the privileges of the **caller**.
- `SECURITY DEFINER`: runs with the privileges of the **function owner**. Like `sudo`.

```sql
CREATE FUNCTION safe_reset_password(p_user text) ...
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, pg_temp      -- ALWAYS set this for SECURITY DEFINER
AS $$ ... $$;

REVOKE ALL ON FUNCTION safe_reset_password(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION safe_reset_password(text) TO app_user;
```

> **Danger:** Without a fixed `search_path`, an attacker can create a fake object with the same name and trick your function. Always set it.

### Other function features

- **Overloading:** Same name, different parameter types.
- **Default values** for parameters.
- **`VARIADIC`** for a list of arguments.
- **`RETURNS SETOF type`** for many rows.
- **`COST` and `ROWS`** hints for the planner.
- List functions in psql: `\df`; show source: `\sf function_name`.

### When to use

- Reuse a calculation (tax, formatting, scoring).
- Triggers need a trigger function (see below).
- Keep data-heavy logic close to the data (fewer round trips).
- Expression indexes need an `IMMUTABLE` function.

### When NOT to use

- Business logic that changes often and needs unit tests and version control may be easier in the application. Choose one place on purpose.
- Do not call a slow function for every row of a big table.

## 13.4 Stored Procedures

### What is it?

A **procedure** is like a function, but:

| | Function | Procedure |
|---|---|---|
| Called with | `SELECT fn()` | `CALL proc()` |
| Returns a value | Yes | No (only `OUT` parameters) |
| Can use `COMMIT` / `ROLLBACK` inside | **No** | **Yes** (PostgreSQL 11+) |

The big reason to use a procedure: **transaction control** inside the code. For example, process 10 million rows in batches and commit after each batch.

### Syntax

```sql
CREATE [OR REPLACE] PROCEDURE proc_name (param type, ...)
LANGUAGE plpgsql
AS $$
BEGIN
  ...
  COMMIT;    -- allowed
END;
$$;

CALL proc_name(args);
DROP PROCEDURE proc_name(types);
```

### Example 1: Place an order (several steps)

```sql
CREATE OR REPLACE PROCEDURE place_order(
  p_customer_id bigint,
  p_product_id  bigint,
  p_quantity    int
)
LANGUAGE plpgsql
AS $$
DECLARE
  v_order_id bigint;
  v_price    numeric;
BEGIN
  SELECT price INTO v_price FROM products WHERE id = p_product_id FOR UPDATE;  -- lock the row
  IF NOT FOUND THEN
    RAISE EXCEPTION 'Product % not found', p_product_id;
  END IF;

  UPDATE products SET stock = stock - p_quantity WHERE id = p_product_id;
  -- the CHECK/your own logic can stop negative stock:
  IF (SELECT stock FROM products WHERE id = p_product_id) < 0 THEN
    RAISE EXCEPTION 'Not enough stock';
  END IF;

  INSERT INTO orders (customer_id, status) VALUES (p_customer_id, 'new')
  RETURNING id INTO v_order_id;

  INSERT INTO order_items (order_id, product_id, quantity, unit_price)
  VALUES (v_order_id, p_product_id, p_quantity, v_price);
END;
$$;

CALL place_order(1, 1, 2);
```

If any step raises an error, **everything is rolled back** (it is all one transaction).

### Example 2: Batch work with COMMIT

```sql
CREATE OR REPLACE PROCEDURE archive_old_orders(p_batch int DEFAULT 1000)
LANGUAGE plpgsql
AS $$
DECLARE
  v_rows int;
BEGIN
  LOOP
    DELETE FROM orders
    WHERE id IN (
      SELECT id FROM orders
      WHERE created_at < now() - interval '2 years'
        AND NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.order_id = orders.id)
      LIMIT p_batch
    );
    GET DIAGNOSTICS v_rows = ROW_COUNT;
    EXIT WHEN v_rows = 0;
    COMMIT;                       -- release locks and let VACUUM work between batches
  END LOOP;
END;
$$;

CALL archive_old_orders(500);
```

> `COMMIT` inside a procedure works only if you call it with `CALL` **outside** an explicit transaction block (`BEGIN ... COMMIT` from the client).

### When to use

- Multi-step jobs, maintenance, batch jobs, data migrations.
- You need commits inside the loop.

### When NOT to use

- A simple calculation that returns a value: use a function.

## 13.5 Triggers

### What is a trigger?

A **trigger** automatically runs a function when something happens to a table (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`). You do not call it. PostgreSQL does.

A trigger has **two parts**:
1. A **trigger function** (returns the special type `trigger`).
2. A **trigger** definition that attaches it to a table.

### Syntax

```sql
-- Part 1: the function
CREATE OR REPLACE FUNCTION my_trigger_fn()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  -- use NEW, OLD, TG_OP, TG_TABLE_NAME ...
  RETURN NEW;       -- or OLD, or NULL
END;
$$;

-- Part 2: the trigger
CREATE TRIGGER trigger_name
{ BEFORE | AFTER | INSTEAD OF } { INSERT | UPDATE [OF col, ...] | DELETE | TRUNCATE } [ OR ... ]
ON table_name
[ FOR EACH ROW | FOR EACH STATEMENT ]
[ WHEN (condition) ]
EXECUTE FUNCTION my_trigger_fn();

DROP TRIGGER trigger_name ON table_name;
ALTER TABLE table_name DISABLE TRIGGER trigger_name;
ALTER TABLE table_name ENABLE TRIGGER trigger_name;
```

### Key words

| Word | Meaning |
|---|---|
| `BEFORE` | Runs **before** the change. You can **change** `NEW` or **cancel** the row. |
| `AFTER` | Runs **after** the change. Good for audit, notifications. |
| `INSTEAD OF` | Only on **views**. Replaces the action. |
| `FOR EACH ROW` | Runs once **per row**. |
| `FOR EACH STATEMENT` | Runs **once per SQL statement**, no matter how many rows. |
| `NEW` | The new row (INSERT, UPDATE). |
| `OLD` | The old row (UPDATE, DELETE). |
| `TG_OP` | Text: `'INSERT'`, `'UPDATE'`, `'DELETE'`, `'TRUNCATE'`. |
| `TG_TABLE_NAME` | The table name. |
| `WHEN (...)` | Run only if the condition is true (efficient). |

### What to RETURN

| Trigger kind | Return |
|---|---|
| `BEFORE ... FOR EACH ROW` | `NEW` (to continue, with your changes), `OLD` for DELETE, or `NULL` to **skip** this row |
| `AFTER` (row or statement) | Value is ignored. Return `NULL` (or `NEW`). |
| `INSTEAD OF` | `NEW` / `OLD` / `NULL` |

### Example 1: Auto-update `updated_at`

```sql
ALTER TABLE products ADD COLUMN updated_at timestamptz NOT NULL DEFAULT now();

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_products_updated_at
BEFORE UPDATE ON products
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();

UPDATE products SET price = 21.99 WHERE name = 'Mouse';
SELECT name, updated_at FROM products;
```

### Example 2: Validate and clean data (BEFORE)

```sql
CREATE OR REPLACE FUNCTION clean_customer()
RETURNS trigger
LANGUAGE plpgsql
AS $$
BEGIN
  NEW.email := lower(trim(NEW.email));
  IF NEW.email NOT LIKE '%@%' THEN
    RAISE EXCEPTION 'Invalid email: %', NEW.email;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_customers_clean
BEFORE INSERT OR UPDATE OF email ON customers
FOR EACH ROW
EXECUTE FUNCTION clean_customer();
```

### Example 3: Only run when a column really changes

```sql
CREATE TRIGGER trg_orders_status_log
AFTER UPDATE ON orders
FOR EACH ROW
WHEN (OLD.status IS DISTINCT FROM NEW.status)
EXECUTE FUNCTION log_status_change();   -- you write this function
```

`IS DISTINCT FROM` treats `NULL` as a normal value (`NULL IS DISTINCT FROM NULL` is false).

### Example 4: INSTEAD OF trigger on a view

```sql
CREATE VIEW customer_summary AS
SELECT c.id, c.name, count(o.id) AS orders
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name;

CREATE OR REPLACE FUNCTION customer_summary_update()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  UPDATE customers SET name = NEW.name WHERE id = OLD.id;
  RETURN NEW;
END; $$;

CREATE TRIGGER trg_customer_summary
INSTEAD OF UPDATE ON customer_summary
FOR EACH ROW EXECUTE FUNCTION customer_summary_update();
```

### Example 5: Statement-level trigger with transition tables (PG 10+)

Look at **all changed rows at once**, with no per-row cost.

```sql
CREATE OR REPLACE FUNCTION log_bulk_delete()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE NOTICE 'Deleted % rows', (SELECT count(*) FROM deleted_rows);
  RETURN NULL;
END; $$;

CREATE TRIGGER trg_orders_bulk_delete
AFTER DELETE ON orders
REFERENCING OLD TABLE AS deleted_rows
FOR EACH STATEMENT
EXECUTE FUNCTION log_bulk_delete();
```

### Order of triggers

If a table has many triggers for the same event, they run in **alphabetical order by name**. `BEFORE` triggers run before `AFTER` triggers.

### Other trigger types

- **Constraint triggers:** `CREATE CONSTRAINT TRIGGER ... DEFERRABLE` (run at commit time).
- **Event triggers:** fire on DDL (`CREATE TABLE`, `DROP`, ...). Example use: block dropping tables in production.

### When to use

- Audit logs (what changed, who, when).
- Automatic columns (`updated_at`).
- Rules too complex for `CHECK` constraints.
- Keep a summary table in sync.

### When NOT to use

- Hidden logic is **hard to debug**. People forget triggers exist.
- Triggers slow down every write. A `FOR EACH ROW` trigger on a bulk load of 10 million rows is slow.
- Prefer `CHECK`, `FOREIGN KEY`, `DEFAULT`, and generated columns when they are enough.
- Avoid triggers that call other triggers in long chains.

## 13.6 Roles and Privileges

### Roles: users and groups are the same thing

In PostgreSQL, a **role** can be a **user** (can log in) or a **group** (holds privileges for others). `CREATE USER` is just `CREATE ROLE ... LOGIN`.

### Syntax

```sql
CREATE ROLE role_name [WITH option ...];
-- options:
--   LOGIN | NOLOGIN          (can connect or not; default for CREATE ROLE is NOLOGIN)
--   PASSWORD 'secret'
--   SUPERUSER | NOSUPERUSER
--   CREATEDB | NOCREATEDB
--   CREATEROLE | NOCREATEROLE
--   INHERIT | NOINHERIT
--   CONNECTION LIMIT n
--   VALID UNTIL 'timestamp'
--   BYPASSRLS | NOBYPASSRLS

CREATE USER app_user WITH PASSWORD 'S3cure!pass';     -- = CREATE ROLE ... LOGIN

ALTER ROLE app_user WITH PASSWORD 'newpass';
ALTER ROLE app_user CONNECTION LIMIT 20;
ALTER ROLE app_user SET statement_timeout = '30s';     -- default setting for this role
ALTER ROLE app_user SET search_path = app, public;
DROP ROLE app_user;                                    -- must own nothing: see REASSIGN OWNED
```

List roles in psql: `\du`

### GRANT and REVOKE

```sql
GRANT privilege [, ...] ON object TO role;
REVOKE privilege [, ...] ON object FROM role;
```

| Object | Privileges |
|---|---|
| Database | `CONNECT`, `CREATE`, `TEMPORARY` |
| Schema | `USAGE` (see inside), `CREATE` (make objects) |
| Table / View | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `REFERENCES`, `TRIGGER` |
| Column | `SELECT (col)`, `INSERT (col)`, `UPDATE (col)` |
| Sequence | `USAGE`, `SELECT`, `UPDATE` |
| Function / Procedure | `EXECUTE` |

```sql
GRANT CONNECT ON DATABASE shop TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE ON orders TO app_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO app_user;           -- existing tables only!
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO app_user;
GRANT EXECUTE ON FUNCTION add_tax(numeric, numeric) TO app_user;

-- Column-level
GRANT SELECT (id, name, country) ON customers TO support_user;      -- cannot see email

-- Take away
REVOKE DELETE ON orders FROM app_user;
REVOKE ALL ON customers FROM app_user;
```

Add `WITH GRANT OPTION` to let the person pass the privilege on to others.

### Default privileges (important!)

`GRANT ... ON ALL TABLES` only affects tables that **exist now**. For **future** tables, use `ALTER DEFAULT PRIVILEGES`:

```sql
-- For tables that role "admin_user" will create in the future
ALTER DEFAULT PRIVILEGES FOR ROLE admin_user IN SCHEMA public
GRANT SELECT ON TABLES TO readonly_role;
```

> It applies only to objects created **by the role named in `FOR ROLE`** (default: the current role).

### Group roles (the clean way)

Give privileges to a **group role**, then add users to the group.

```sql
CREATE ROLE readonly_role NOLOGIN;
GRANT CONNECT ON DATABASE shop TO readonly_role;
GRANT USAGE ON SCHEMA public TO readonly_role;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly_role;

CREATE USER alice WITH PASSWORD '...';
GRANT readonly_role TO alice;          -- alice is now a member
-- REVOKE readonly_role FROM alice;
```

If a role was created with `NOINHERIT`, the member must run `SET ROLE readonly_role;` to use the group's rights.

### Built-in roles (predefined)

| Role | Purpose |
|---|---|
| `pg_read_all_data` (PG 14+) | Read all tables, views, sequences |
| `pg_write_all_data` (PG 14+) | Write all tables |
| `pg_monitor` | Read monitoring views (`pg_stat_*`) |
| `pg_read_all_stats` | Read all statistics |
| `pg_signal_backend` | Cancel or terminate other sessions |
| `pg_read_server_files` / `pg_write_server_files` | Dangerous: file access on the server |

```sql
GRANT pg_read_all_data TO analyst;      -- quick read-only access to everything
GRANT pg_monitor TO monitoring_user;
```

### The `public` schema

- Every role is a member of the special pseudo-role `PUBLIC` (means "everybody").
- Before PostgreSQL 15, everyone could create tables in the `public` schema. **From PG 15, they cannot.** On older versions, run:
  ```sql
  REVOKE CREATE ON SCHEMA public FROM PUBLIC;
  REVOKE ALL ON DATABASE shop FROM PUBLIC;     -- so only granted roles can connect
  ```

### Ownership

The role that creates an object **owns** it. The owner can do anything with it and grant to others.

```sql
ALTER TABLE orders OWNER TO admin_user;
REASSIGN OWNED BY old_user TO new_user;     -- before dropping a role
DROP OWNED BY old_user;
```

### Login security: `pg_hba.conf` and passwords

`pg_hba.conf` says **who** can connect, from **where**, and **how** they prove it.

```
# TYPE   DATABASE   USER         ADDRESS          METHOD
local    all        postgres                      peer
host     shop       app_user     10.0.0.0/24      scram-sha-256
host     all        all          0.0.0.0/0        reject
hostssl  shop       readonly     0.0.0.0/0        scram-sha-256
```

- Rules are read **top to bottom**; the first match wins.
- Use **`scram-sha-256`**. Avoid `md5` and never use `trust` on a real server.
- Make sure `password_encryption = scram-sha-256` (default since PG 14).
- Reload after editing: `SELECT pg_reload_conf();`
- Use `hostssl` and turn on `ssl = on` so passwords and data are encrypted on the network.

### Check privileges

```sql
\dp customers                                  -- table privileges
\du                                            -- roles
SELECT has_table_privilege('alice','customers','SELECT');
SELECT * FROM information_schema.role_table_grants WHERE grantee = 'alice';
```

### Best practices

1. **Least privilege:** give only what is needed.
2. The app should **not** connect as a superuser or as the table owner.
3. Use separate roles: `migration_user` (owns tables, runs Flyway), `app_user` (DML only), `readonly_user` (reports).
4. Use group roles.
5. Set `statement_timeout` and `idle_in_transaction_session_timeout` per role.

## 13.7 Row-Level Security (RLS)

### What is it?

Normal `GRANT` works on a **whole table**. **RLS** works on **rows**: it lets each user see or change only certain rows. Perfect for **multi-tenant** apps ("customer A must never see customer B's data").

### Syntax

```sql
ALTER TABLE table_name ENABLE ROW LEVEL SECURITY;
ALTER TABLE table_name FORCE ROW LEVEL SECURITY;      -- also apply to the table OWNER

CREATE POLICY policy_name ON table_name
  [ AS { PERMISSIVE | RESTRICTIVE } ]
  [ FOR { ALL | SELECT | INSERT | UPDATE | DELETE } ]
  [ TO role_name [, ...] ]
  [ USING ( condition_for_existing_rows ) ]
  [ WITH CHECK ( condition_for_new_rows ) ];

DROP POLICY policy_name ON table_name;
ALTER TABLE table_name DISABLE ROW LEVEL SECURITY;
```

### Key ideas

| Word | Meaning |
|---|---|
| `USING (...)` | Which **existing** rows the user can **see / update / delete**. |
| `WITH CHECK (...)` | Which **new or changed** rows the user may **write**. |
| `PERMISSIVE` (default) | Policies are combined with **OR**. |
| `RESTRICTIVE` | Policies are combined with **AND** (must also pass). |
| Default when RLS is on and no policy exists | **Deny all** (the owner and superusers still bypass it, unless `FORCE`). |

**Who bypasses RLS?**
- Superusers.
- Roles with `BYPASSRLS`.
- The **table owner** (unless you use `FORCE ROW LEVEL SECURITY`).

### Example: Multi-tenant table

```sql
CREATE TABLE invoices (
  id        bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id int  NOT NULL,
  amount    numeric(10,2) NOT NULL,
  note      text
);
INSERT INTO invoices (tenant_id, amount, note)
VALUES (1, 100, 'tenant 1 - a'), (1, 250, 'tenant 1 - b'), (2, 999, 'tenant 2 - secret');

CREATE ROLE tenant_app LOGIN PASSWORD 'tenantpass';
GRANT SELECT, INSERT, UPDATE, DELETE ON invoices TO tenant_app;
GRANT USAGE ON ALL SEQUENCES IN SCHEMA public TO tenant_app;

ALTER TABLE invoices ENABLE ROW LEVEL SECURITY;
ALTER TABLE invoices FORCE  ROW LEVEL SECURITY;

-- The app tells the database which tenant it is, using a session setting
CREATE POLICY tenant_isolation ON invoices
  FOR ALL
  TO tenant_app
  USING      (tenant_id = current_setting('app.tenant_id')::int)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::int);
```

Test as `tenant_app`:

```sql
SET ROLE tenant_app;
SET app.tenant_id = '1';
SELECT * FROM invoices;                       -- only tenant 1 rows
INSERT INTO invoices (tenant_id, amount) VALUES (2, 5);
-- ERROR: new row violates row-level security policy for table "invoices"
RESET ROLE;
```

In an app, use a transaction-local setting so it cannot leak between pooled connections:

```sql
BEGIN;
SELECT set_config('app.tenant_id', '1', true);   -- true = local to this transaction
SELECT * FROM invoices;
COMMIT;
```

> The safe version of `current_setting` for a missing value: `current_setting('app.tenant_id', true)` returns `NULL` instead of an error. A `NULL` comparison means **no rows**, which is a safe default.

### Example: Users see their own rows by username

```sql
CREATE POLICY own_rows ON some_table
  USING (owner_name = current_user);
```

### Example: Separate policies per command

```sql
CREATE POLICY select_all   ON invoices FOR SELECT USING (true);
CREATE POLICY modify_own   ON invoices FOR UPDATE USING (tenant_id = 1) WITH CHECK (tenant_id = 1);
```

### Performance and safety tips

- Add an **index** on the column used in the policy (like `tenant_id`).
- Keep policy expressions simple and fast; they run for every row.
- Views run with the **owner's** rights, so they can bypass RLS. In PG 15+, use `security_invoker = true`.
- RLS does not protect against a **superuser** or a role with `BYPASSRLS`.
- Check policies: `\d+ invoices` or `SELECT * FROM pg_policies;`

### When to use

- Multi-tenant SaaS, data isolation by user, department, or region.
- You want the database to enforce the rule even if the application has a bug.

### When NOT to use

- Simple apps with one trust level.
- If you cannot test it well. A wrong policy can silently hide data.

## 13.8 Full-Text Search

### What is it?

Full-text search (FTS) finds **documents** that match **words**, with smart rules: it ignores case, removes tiny words (like "the"), and reduces words to their root ("running" → "run"). It is far better than `LIKE '%word%'` for text.

### Two main types

| Type | What it holds |
|---|---|
| `tsvector` | The **document**, as a sorted list of simplified words (called **lexemes**) with positions |
| `tsquery` | The **search question**, with `&` (and), `\|` (or), `!` (not), `<->` (followed by) |

```sql
SELECT to_tsvector('english', 'The quick brown foxes were running fast');
-- 'brown':3 'fast':7 'fox':4 'quick':2 'run':6
-- "the" and "were" are stop words (removed). "foxes" → "fox", "running" → "run".

SELECT to_tsquery('english', 'running & fox');
-- 'run' & 'fox'
```

### The match operator: `@@`

```sql
SELECT to_tsvector('english', 'The quick brown foxes')
       @@ to_tsquery('english', 'fox & quick');       -- true
```

### Ways to build a query

| Function | Behavior | Example input |
|---|---|---|
| `to_tsquery` | You write operators yourself. Strict syntax. | `'postgres & (index \| search)'` |
| `plainto_tsquery` | Plain words, all joined with AND. Safe for user input. | `'postgres index'` |
| `phraseto_tsquery` | Words must be next to each other. | `'full text search'` |
| `websearch_to_tsquery` (PG 11+) | Google-like: quotes, `or`, `-word`. **Best for search boxes.** | `'"full text" -mysql or postgres'` |

```sql
SELECT websearch_to_tsquery('english', '"full text" search -mysql');
```

### Example: Search an articles table

```sql
CREATE TABLE articles (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title  text NOT NULL,
  body   text NOT NULL,
  search tsvector GENERATED ALWAYS AS (
           setweight(to_tsvector('english', coalesce(title,'')), 'A') ||
           setweight(to_tsvector('english', coalesce(body ,'')), 'B')
         ) STORED
);

CREATE INDEX idx_articles_search ON articles USING gin (search);

INSERT INTO articles (title, body) VALUES
 ('PostgreSQL Indexes',  'Indexes make queries fast. B-tree is the default index type.'),
 ('Backup and Restore',  'Use pg_dump to back up a database and pg_restore to restore it.'),
 ('Replication Basics',  'Streaming replication copies WAL to a standby server.');

SELECT id, title
FROM articles
WHERE search @@ websearch_to_tsquery('english', 'backup restore');
```

- A **generated column** keeps the `tsvector` up to date automatically (PG 12+). On older versions, use a trigger with `tsvector_update_trigger`.
- **`GIN` index** on the `tsvector` makes the search fast.
- **`setweight`** gives labels `A` (most important) to `D` (least). Words in the title count more than words in the body.

### Rank the results

```sql
SELECT id, title,
       ts_rank(search, q) AS rank
FROM articles, websearch_to_tsquery('english', 'index fast') AS q
WHERE search @@ q
ORDER BY rank DESC
LIMIT 10;
```

- `ts_rank` counts how often and where words appear.
- `ts_rank_cd` also considers how close the words are.

### Highlight the matches

```sql
SELECT ts_headline('english', body, q,
                   'StartSel=<b>, StopSel=</b>, MaxWords=20, MinWords=5')
FROM articles, websearch_to_tsquery('english', 'index') AS q
WHERE search @@ q;
```

`ts_headline` is slow on big texts. Run it only on the final few rows (after `LIMIT`).

### Without a stored column (expression index)

```sql
CREATE INDEX idx_articles_expr
ON articles USING gin (to_tsvector('english', title || ' ' || body));

SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body) @@ plainto_tsquery('english', 'index');
```

The expression in the query must be **exactly** the same as in the index. Always pass the language name (`'english'`).

### Prefix search (type-ahead)

```sql
SELECT * FROM articles WHERE search @@ to_tsquery('english', 'repli:*');   -- replication, replica...
```

### Languages and dictionaries

```sql
SELECT cfgname FROM pg_ts_config;                        -- available languages
SELECT * FROM ts_debug('english', 'The foxes are running');   -- see how text is processed
SHOW default_text_search_config;
```

Use `'simple'` as the language to skip stop words and stemming (good for names, codes).

### FTS vs other options

| Need | Use |
|---|---|
| Word search with ranking | **Full-text search (GIN)** |
| Substring / typo-friendly (`%abc%`) | `pg_trgm` + GIN |
| Exact prefix `LIKE 'abc%'` | B-tree with `text_pattern_ops` |
| Very advanced search (facets, synonyms, huge scale) | A search engine (Elasticsearch, OpenSearch) |

### When NOT to use

- FTS does not do spelling mistakes ("postgre" ≠ "postgres"). Add `pg_trgm` for similarity (`similarity()`, `%` operator).

## 13.9 Hands-on: Create an Audit Trigger

**Goal:** Every `INSERT`, `UPDATE`, and `DELETE` on important tables is saved in an `audit_log` table: **what** changed, **who** changed it, **when**, the **old** values and the **new** values.

### Step 1: Create the audit table

```sql
CREATE SCHEMA IF NOT EXISTS audit;

CREATE TABLE audit.audit_log (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  changed_at  timestamptz NOT NULL DEFAULT now(),
  table_name  text        NOT NULL,
  operation   text        NOT NULL,           -- INSERT / UPDATE / DELETE
  row_id      text,                           -- primary key value of the changed row
  db_user     text        NOT NULL DEFAULT session_user,
  app_user    text,                           -- who the app says it is
  txid        bigint      NOT NULL DEFAULT txid_current(),
  old_data    jsonb,
  new_data    jsonb,
  changed_cols jsonb                          -- only the columns that changed (for UPDATE)
);

CREATE INDEX ON audit.audit_log (table_name, changed_at DESC);
CREATE INDEX ON audit.audit_log (row_id);
```

### Step 2: Create one generic trigger function

```sql
CREATE OR REPLACE FUNCTION audit.log_change()
RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = audit, public, pg_temp
AS $$
DECLARE
  v_old  jsonb;
  v_new  jsonb;
  v_diff jsonb;
  v_id   text;
BEGIN
  IF TG_OP = 'INSERT' THEN
    v_new := to_jsonb(NEW);
    v_id  := v_new ->> 'id';

  ELSIF TG_OP = 'UPDATE' THEN
    v_old := to_jsonb(OLD);
    v_new := to_jsonb(NEW);
    v_id  := v_new ->> 'id';
    -- keep only the columns whose value changed
    SELECT jsonb_object_agg(n.key, n.value)
      INTO v_diff
      FROM jsonb_each(v_new) n
      WHERE v_old -> n.key IS DISTINCT FROM n.value;
    IF v_diff IS NULL THEN
      RETURN NEW;                         -- nothing changed: do not log
    END IF;

  ELSIF TG_OP = 'DELETE' THEN
    v_old := to_jsonb(OLD);
    v_id  := v_old ->> 'id';
  END IF;

  INSERT INTO audit.audit_log
    (table_name, operation, row_id, app_user, old_data, new_data, changed_cols)
  VALUES
    (TG_TABLE_SCHEMA || '.' || TG_TABLE_NAME, TG_OP, v_id,
     current_setting('app.user_id', true),         -- NULL if not set
     v_old, v_new, v_diff);

  RETURN NULL;       -- AFTER trigger: return value is ignored
END;
$$;
```

Why `SECURITY DEFINER`? So normal users can cause audit rows to be written **without** having direct rights on the audit table.

### Step 3: Attach the trigger to tables

```sql
CREATE TRIGGER trg_audit_customers
AFTER INSERT OR UPDATE OR DELETE ON customers
FOR EACH ROW EXECUTE FUNCTION audit.log_change();

CREATE TRIGGER trg_audit_products
AFTER INSERT OR UPDATE OR DELETE ON products
FOR EACH ROW EXECUTE FUNCTION audit.log_change();
```

### Step 4: Test it

```sql
-- Tell the database who the app user is (just for this transaction)
BEGIN;
SELECT set_config('app.user_id', 'asha@company.com', true);

INSERT INTO customers (name, email) VALUES ('Dev', 'dev@example.com');
UPDATE customers SET country = 'DE' WHERE email = 'dev@example.com';
UPDATE customers SET country = 'DE' WHERE email = 'dev@example.com';   -- no change: not logged
DELETE FROM customers WHERE email = 'dev@example.com';
COMMIT;

SELECT changed_at, table_name, operation, row_id, app_user, changed_cols
FROM audit.audit_log
ORDER BY id;
```

### Step 5: Protect the audit log

An audit log is useless if people can edit it.

```sql
REVOKE ALL ON audit.audit_log FROM PUBLIC;
REVOKE UPDATE, DELETE, TRUNCATE ON audit.audit_log FROM app_user;   -- if app_user exists

-- Optional extra: block UPDATE/DELETE even for the owner with a trigger
CREATE OR REPLACE FUNCTION audit.block_changes()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'audit_log is append-only';
END; $$;

CREATE TRIGGER trg_audit_log_immutable
BEFORE UPDATE OR DELETE ON audit.audit_log
FOR EACH ROW EXECUTE FUNCTION audit.block_changes();
```

### Notes and tips

- Triggers add **write cost**. Audit only important tables.
- The audit table grows fast. **Partition** it by month and drop old partitions (see Phase 4).
- Use `WHEN (OLD.* IS DISTINCT FROM NEW.*)` on the trigger to skip no-op updates cheaply.
- `TRUNCATE` does not fire row triggers. Add a separate `FOR EACH STATEMENT` trigger if needed.
- For more advanced audit needs, look at the `pgaudit` extension (logs statements to the server log).

## 13.10 Hands-on: Create a Read-Only Role

**Goal:** A user `report_user` can log in and **read** everything in the `shop` database, but cannot change anything.

### Step 1: Create the group role and the user

```sql
CREATE ROLE readonly_role NOLOGIN;                    -- the "group"

CREATE ROLE report_user LOGIN PASSWORD 'ChangeMe!123'
  CONNECTION LIMIT 10;                                -- the real person/app

GRANT readonly_role TO report_user;
```

### Step 2: Give read access

Replace `shop` with your database name (run `SELECT current_database();`).

```sql
GRANT CONNECT ON DATABASE shop TO readonly_role;

GRANT USAGE ON SCHEMA public TO readonly_role;
GRANT SELECT ON ALL TABLES    IN SCHEMA public TO readonly_role;
GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO readonly_role;

-- Also for tables created in the future by the owner (use the real owner role name):
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES    TO readonly_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON SEQUENCES TO readonly_role;
```

> **Shortcut (PG 14+):** `GRANT pg_read_all_data TO report_user;` gives read access to **all** tables in **all** schemas, now and in the future.

### Step 3: Add safety belts

```sql
ALTER ROLE report_user SET default_transaction_read_only = on;   -- every session starts read-only
ALTER ROLE report_user SET statement_timeout = '60s';            -- stop runaway queries
ALTER ROLE report_user SET idle_in_transaction_session_timeout = '5min';

-- Hide sensitive columns: grant only specific columns instead of the whole table
REVOKE SELECT ON customers FROM readonly_role;
GRANT  SELECT (id, name, country, created_at) ON customers TO readonly_role;   -- no email
```

### Step 4: Test it

```bash
$ psql -h localhost -U report_user -d shop
```
```sql
SELECT count(*) FROM orders;                        -- works
SELECT email FROM customers;                        -- ERROR: permission denied for column email
INSERT INTO products (name, price) VALUES ('X', 1); -- ERROR: permission denied for table products
CREATE TABLE t (id int);                            -- ERROR: permission denied for schema public
```

Or test from a superuser session without logging in again:

```sql
SET ROLE report_user;
DELETE FROM orders;        -- ERROR: permission denied
RESET ROLE;
```

### Step 5: Check what the role can do

```sql
SELECT has_table_privilege('report_user', 'orders',   'SELECT');   -- true
SELECT has_table_privilege('report_user', 'orders',   'INSERT');   -- false
SELECT * FROM information_schema.role_table_grants WHERE grantee = 'readonly_role';
```

### Step 6: Remove the role (clean up)

```sql
REVOKE ALL ON ALL TABLES IN SCHEMA public FROM readonly_role;
REVOKE ALL ON SCHEMA public FROM readonly_role;
REVOKE ALL ON DATABASE shop FROM readonly_role;
ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE SELECT ON TABLES FROM readonly_role;
DROP OWNED BY readonly_role;
DROP ROLE report_user;
DROP ROLE readonly_role;
```

**Also remember:** a read-only **role** is not enough if the user can reach the server from anywhere. Also limit access in `pg_hba.conf` (specific IPs, `scram-sha-256`, SSL).

# Day 14: Backup, Replication and Capstone

Today is about keeping your data **safe** and **available**, making your app **talk to** the database in the right way, and putting everything together in one project.

**Remember:** a backup you have never restored is **not** a backup. It is only a hope.

---

## Backup methods at a glance

| Method | Type | Good for | Can do point-in-time recovery? |
|---|---|---|---|
| `pg_dump` / `pg_restore` | **Logical** (SQL or custom format) | Small/medium DBs, one database or one table, moving between versions | No |
| `pg_basebackup` + WAL archive | **Physical** (copy of files) | Big DBs, fast restore, disaster recovery | **Yes** |
| Streaming replication | **Physical, live copy** | High availability, read replicas | No (it copies mistakes too!) |
| Logical replication | **Logical, live** | Upgrades, copy some tables | No |

> **Replication is not backup.** If someone runs `DROP TABLE`, the replica drops it a moment later. You still need backups.

---

## 14.1 Logical Backups: pg_dump and pg_restore

### What is it?

`pg_dump` reads your database and writes **instructions** (SQL commands or a special archive) that can rebuild it. It takes a **consistent snapshot**, even while users are writing, and it does **not** block normal reads and writes.

### Syntax

```bash
pg_dump [connection options] [options] dbname > file
pg_restore [connection options] [options] file
```

**Connection options:** `-h host`, `-p port`, `-U user`, `-d dbname`, `-W` (ask password).
To avoid typing a password, use a `~/.pgpass` file (`host:port:db:user:password`, permission `0600`) or the `PGPASSWORD` variable (not for production).

### Output formats

| Flag | Format | File | Restore with | Parallel dump | Parallel restore | Choose tables on restore |
|---|---|---|---|---|---|---|
| `-Fp` (default) | **plain** SQL text | `.sql` | `psql` | No | No | No |
| `-Fc` | **custom** (compressed) | `.dump` | `pg_restore` | No | **Yes** | **Yes** |
| `-Fd` | **directory** | folder | `pg_restore` | **Yes** (`-j`) | **Yes** | **Yes** |
| `-Ft` | **tar** | `.tar` | `pg_restore` | No | No | Yes |

**Best choice:** `-Fc` for most cases, `-Fd -j N` for big databases.

### Most used pg_dump options

| Option | Meaning |
|---|---|
| `-s` / `--schema-only` | Only structure (tables, indexes), no data |
| `-a` / `--data-only` | Only data |
| `-t table` | Only this table (can repeat) |
| `-T table` | Exclude this table |
| `-n schema` / `-N schema` | Include / exclude a schema |
| `--exclude-table-data=table` | Keep the table structure but skip its data |
| `-j N` | N parallel jobs (directory format only) |
| `-Z 0-9` | Compression level |
| `-c` / `--clean` | Add `DROP` commands before `CREATE` |
| `--if-exists` | Use with `--clean`: no error if object is missing |
| `-C` / `--create` | Add `CREATE DATABASE` to the output |
| `--no-owner` | Do not set object owners (handy when restoring as a different user) |
| `--no-privileges` | Skip `GRANT` and `REVOKE` |
| `--inserts` | Use `INSERT` instead of `COPY` (slow, but portable) |
| `-v` | Verbose (show progress) |
| `-f file` | Output file name |

### Examples

```bash
# 1) Plain SQL file
$ pg_dump -h localhost -U postgres -d shop -f shop.sql

# 2) Custom format (recommended)
$ pg_dump -h localhost -U postgres -d shop -Fc -f shop.dump

# 3) Directory format, 4 parallel jobs (fastest for big DBs)
$ pg_dump -h localhost -U postgres -d shop -Fd -j 4 -f shop_dir

# 4) Only the structure
$ pg_dump -U postgres -d shop -s -f shop_schema.sql

# 5) One table only
$ pg_dump -U postgres -d shop -t public.orders -Fc -f orders.dump

# 6) Everything except a big log table's data
$ pg_dump -U postgres -d shop -Fc --exclude-table-data=audit.audit_log -f shop.dump
```

### pg_dumpall: roles and global objects

`pg_dump` does **not** save **roles** (users) or **tablespaces**. They belong to the whole server.

```bash
$ pg_dumpall -U postgres --globals-only > globals.sql     # roles + tablespaces
$ pg_dumpall -U postgres > everything.sql                 # every database (plain SQL only)
```

Always save `globals.sql` together with your database dumps.

### Restoring

**Plain SQL file → psql:**
```bash
$ createdb -U postgres shop_restored
$ psql -U postgres -d shop_restored -v ON_ERROR_STOP=1 -f shop.sql
```
`ON_ERROR_STOP=1` stops at the first error (otherwise psql keeps going and you may not notice problems).

**Custom / directory / tar → pg_restore:**
```bash
# Restore into a new, empty database
$ createdb -U postgres shop_restored
$ pg_restore -U postgres -d shop_restored -v shop.dump

# Parallel restore (4 jobs) - much faster
$ pg_restore -U postgres -d shop_restored -j 4 shop.dump

# Create the database automatically (connect to "postgres" db first)
$ pg_restore -U postgres -C -d postgres shop.dump

# Clean existing objects first
$ pg_restore -U postgres -d shop --clean --if-exists shop.dump

# Restore one table only
$ pg_restore -U postgres -d shop_restored -t orders shop.dump

# Only structure / only data
$ pg_restore -U postgres -d shop_restored --schema-only shop.dump
$ pg_restore -U postgres -d shop_restored --data-only   shop.dump

# Stop at first error / run everything in ONE transaction (cannot be used with -j)
$ pg_restore -U postgres -d shop_restored --exit-on-error shop.dump
$ pg_restore -U postgres -d shop_restored --single-transaction shop.dump

# Look inside the dump (table of contents)
$ pg_restore -l shop.dump > toc.txt
# Edit toc.txt (put ; in front of lines you want to skip), then:
$ pg_restore -U postgres -d shop_restored -L toc.txt shop.dump
```

### After a restore: always do this

```sql
ANALYZE;          -- statistics are NOT included in a dump
```
And check row counts, indexes, and that the app can connect.

### Important notes

- A dump is a **snapshot at the moment the dump started**. Changes after that are not included.
- You can restore into a **newer** PostgreSQL version (this is a common upgrade method). Restoring to an **older** version may fail.
- Use the **same or newer** `pg_dump` version than the server.
- Large databases (hundreds of GB) take a long time to dump and restore. Use physical backups for those.
- `pg_dump` holds a lock that blocks `ALTER TABLE` / `DROP TABLE` while it runs. Avoid schema changes during a dump.
- Automate with `cron` and **copy the files off the server** (another machine or object storage like S3). Test restores regularly.

### Example backup script

```bash
#!/bin/bash
set -euo pipefail
DB=shop
DIR=/backups
STAMP=$(date +%F_%H%M)

pg_dump -U postgres -Fc -d "$DB" -f "$DIR/${DB}_${STAMP}.dump"
pg_dumpall -U postgres --globals-only > "$DIR/globals_${STAMP}.sql"

# Keep only last 7 days
find "$DIR" -type f -mtime +7 -delete
```

### When to use / not use

- **Use** for: small to medium databases, migrations, copying data to a test server, backing up one table, upgrading versions.
- **Do not rely only on it** for: very large databases, or when you need to restore to "10:42 AM yesterday" (use PITR).

## 14.2 WAL (Write-Ahead Log)

### What is it?

**WAL** is a log of **every change** made to the database. The rule: **write the change to the WAL (on disk) first, then change the data files later.** That is why it is called "write-ahead".

Why this design?
1. **Crash safety:** If the server crashes, PostgreSQL **replays** the WAL on startup and fixes everything.
2. **Speed:** Writing a log in order (sequential write) is fast. The data files are updated later in the background.
3. **Replication and backup:** Other servers can read the same WAL to copy changes or to recover to any point in time.

### How a write works

```
Your INSERT
   │
   ▼
1. Change in shared memory (shared_buffers)       ← "dirty page"
2. Record written to WAL buffer → WAL file on disk (fsync on COMMIT)
3. COMMIT returns "OK" to you    ← data is safe because the WAL is safe
   │
   ▼  (later, in the background)
4. Checkpoint / background writer writes dirty pages to the data files
```

### Where is it?

- Folder: `$PGDATA/pg_wal/` (in PG 9.x it was `pg_xlog`; never delete files there by hand!).
- Files are **16 MB** each by default, with names like `000000010000000000000003`.
- **LSN** (Log Sequence Number) is a position in the WAL, like `0/3000148`.

### Checkpoints

A **checkpoint** writes all dirty pages to the data files. After a checkpoint, older WAL is no longer needed for crash recovery (but may be kept for archiving or replicas).

Checkpoint happens when `checkpoint_timeout` passes (default 5 min) or WAL size reaches `max_wal_size` (default 1 GB).

### Useful commands

```sql
SELECT pg_current_wal_lsn();                       -- current write position
SELECT pg_walfile_name(pg_current_wal_lsn());      -- which file
SELECT pg_switch_wal();                            -- force a switch to a new WAL file

-- How many bytes of WAL did a test produce?
SELECT pg_current_wal_lsn() AS before \gset
INSERT INTO products (name, price) SELECT 'p' || g, 1 FROM generate_series(1, 10000) g;
SELECT pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), :'before'));
```

```bash
# Read WAL content (human-readable)
$ pg_waldump /var/lib/postgresql/16/main/pg_wal/000000010000000000000003 | head
```

```sql
SHOW wal_level;
SELECT * FROM pg_stat_wal;                       -- WAL statistics (PG 14+)
```

### Important WAL settings

| Setting | Default | Meaning |
|---|---|---|
| `wal_level` | `replica` | `minimal` (no replication), `replica` (replication + archiving), `logical` (logical replication). Restart needed. |
| `fsync` | on | **Never turn off** in real systems. It makes crash recovery unsafe. |
| `synchronous_commit` | on | `on` = wait until WAL is on disk. `off` = faster, but you may lose the last ~0.6 s of commits on a crash (no corruption). |
| `full_page_writes` | on | Writes a whole page after a checkpoint to protect against torn pages. Keep on. |
| `wal_compression` | off | Compress full-page images. Can lower WAL volume. |
| `max_wal_size` | 1GB | Soft limit that triggers checkpoints. Raise it for write-heavy systems (e.g. 4GB-16GB). |
| `min_wal_size` | 80MB | Keep at least this much WAL for reuse. |
| `checkpoint_timeout` | 5min | Max time between checkpoints. |
| `checkpoint_completion_target` | 0.9 | Spread the checkpoint writes over this fraction of the interval. |
| `wal_keep_size` | 0 | Keep extra WAL for standbys that fall behind. |
| `archive_mode` / `archive_command` | off | Copy finished WAL files to a safe place (for PITR). |

### Warning: WAL disk full

If WAL cannot be removed (because archiving fails, or a **replication slot** is stuck, or a standby is far behind), `pg_wal` grows until the disk is **full**, and PostgreSQL **stops**. Monitor it. See `pg_replication_slots` and use `max_slot_wal_keep_size` (PG 13+) as a safety limit.

## 14.3 Physical Backups: pg_basebackup

### What is it?

`pg_basebackup` copies the **whole data directory** (the real files) from a running server. It is the starting point for **PITR** and for **building a standby server**.

### Syntax

```bash
pg_basebackup -h host -p 5432 -U replication_user -D /path/to/backup [options]
```

| Option | Meaning |
|---|---|
| `-D dir` | Where to put the backup |
| `-Ft` | Tar format (`-Fp` = plain files, default) |
| `-z` | Compress (with tar) |
| `-X stream` | Include the WAL needed to make the backup consistent (**recommended**) |
| `-P` | Show progress |
| `-R` | Write standby settings (`standby.signal` + `primary_conninfo`) for building a replica |
| `-C -S slotname` | Create a replication slot and use it |
| `--checkpoint=fast` | Do not wait for a normal checkpoint |
| `-v` | Verbose |

### Requirements

1. A role with the `REPLICATION` privilege:
   ```sql
   CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'ReplPass!234';
   ```
2. A line in `pg_hba.conf` (note the database name is the word `replication`):
   ```
   host  replication  replicator  10.0.0.0/24  scram-sha-256
   ```
3. `max_wal_senders` ≥ 2 (default 10) and `wal_level = replica` or higher.

### Example

```bash
$ pg_basebackup -h localhost -U replicator -D /backups/base_2026_10_30 \
    -Ft -z -X stream -P --checkpoint=fast
```

You get `base.tar.gz` and `pg_wal.tar.gz`. To restore, unpack them into an **empty** data directory and start PostgreSQL.

### Logical vs physical

| | pg_dump (logical) | pg_basebackup (physical) |
|---|---|---|
| What it copies | SQL objects and rows | Raw data files |
| Whole server needed? | Can do a single database or table | **Whole cluster** only |
| Restore speed (big DB) | Slow (rebuilds indexes) | **Fast** (just copy files) |
| Version flexibility | Can restore to a newer version | **Same major version only** |
| PITR | No | **Yes** (with WAL archive) |

## 14.4 Point-in-Time Recovery (PITR)

### What is it?

PITR lets you restore the database to **any moment** you choose, such as "5 minutes before someone ran `DELETE FROM orders` without a `WHERE`".

### How it works

```
   Base backup            WAL files archived continuously
 (Sunday 02:00)  ──►  ... ── ── ── ── ── ── ── ── ── ──►
        │                                       ▲
        │                       ✖ mistake at Tuesday 10:42
        ▼
 Restore the base backup, then REPLAY the WAL
 only up to Tuesday 10:41:59  → data is back
```

You need **two things**:
1. A **base backup** (`pg_basebackup`).
2. A **continuous archive of WAL files** made after that backup.

### Step 1: Turn on WAL archiving (on the live server)

In `postgresql.conf`:

```ini
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /wal_archive/%f && cp %p /wal_archive/%f'
archive_timeout = 300          # force a WAL switch at least every 5 min (limits data loss)
```

- `%p` = path of the WAL file; `%f` = file name only.
- The command must return **exit code 0 only if** the file is safely stored.
- In real systems, send files to another machine or to cloud storage. Tools like **pgBackRest**, **WAL-G**, or **Barman** do this well (with compression, encryption, retention).
- `archive_mode` needs a **restart**. `archive_command` needs a reload.

```bash
$ mkdir -p /wal_archive && chown postgres:postgres /wal_archive
```
```sql
SELECT * FROM pg_stat_archiver;      -- check last_archived_wal and failed_count
```

### Step 2: Take a base backup

```bash
$ pg_basebackup -U replicator -D /backups/base -Ft -z -X stream -P
```

### Step 3: Simulate a disaster (practice only!)

```sql
-- note the time BEFORE the mistake
SELECT now();                                    -- e.g. 2026-10-30 10:41:00+00
SELECT pg_switch_wal();                          -- make sure the WAL is archived
DELETE FROM orders;                              -- OOPS!
SELECT pg_switch_wal();
```

### Step 4: Recover

1. **Stop** PostgreSQL.
   ```bash
   $ sudo systemctl stop postgresql
   ```
2. **Move away** the broken data directory (keep it, just in case).
   ```bash
   $ mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main_broken
   $ mkdir /var/lib/postgresql/16/main && chmod 700 /var/lib/postgresql/16/main
   ```
3. **Unpack the base backup**.
   ```bash
   $ tar -xzf /backups/base/base.tar.gz -C /var/lib/postgresql/16/main
   $ rm -rf /var/lib/postgresql/16/main/pg_wal/*          # old WAL from the backup folder
   $ tar -xzf /backups/base/pg_wal.tar.gz -C /var/lib/postgresql/16/main/pg_wal
   $ chown -R postgres:postgres /var/lib/postgresql/16/main
   ```
4. **Tell PostgreSQL how to recover.** Add to `postgresql.conf`:
   ```ini
   restore_command = 'cp /wal_archive/%f %p'
   recovery_target_time = '2026-10-30 10:41:00+00'
   recovery_target_action = 'promote'       # or 'pause' to look first
   ```
5. **Create the signal file** `recovery.signal` (PG 12+):
   ```bash
   $ touch /var/lib/postgresql/16/main/recovery.signal
   ```
6. **Start** PostgreSQL. It replays WAL until the target, then promotes itself to normal mode.
   ```bash
   $ sudo systemctl start postgresql
   ```
7. **Check the data**, then finish:
   ```sql
   SELECT count(*) FROM orders;
   ```
   With `recovery_target_action = 'pause'`, the server stays read-only so you can check; run `SELECT pg_wal_replay_resume();` to promote when you are happy. If the target was too late or too early, restore again with a different time.

### Recovery targets (choose one)

| Setting | Meaning |
|---|---|
| `recovery_target_time` | Stop at a timestamp |
| `recovery_target_xid` | Stop at a transaction ID |
| `recovery_target_lsn` | Stop at a WAL position |
| `recovery_target_name` | Stop at a named restore point (`SELECT pg_create_restore_point('before_migration');`) |
| `recovery_target = 'immediate'` | Stop as soon as the backup is consistent |
| `recovery_target_inclusive` | Include (`on`, default) or exclude (`off`) the target itself |
| (none) | Replay **all** WAL (recover to the latest point) |

**Tip:** Before a risky change, create a named restore point:
```sql
SELECT pg_create_restore_point('before_big_migration');
```

### Timelines

After a PITR promote, PostgreSQL starts a **new timeline** (a new "branch" of history). WAL file names start with the timeline number (`00000002...`). This stops the new history from mixing with the old one. If you need a specific timeline: `recovery_target_timeline = 'latest'` (default in PG 12+).

### Rules for good PITR

- **Test the restore** on a separate machine regularly.
- Keep base backups **and** all WAL since the oldest base backup you might use.
- Monitor `pg_stat_archiver` for failures.
- `archive_timeout` limits how much you can lose if the server dies.
- Use a tool (pgBackRest / WAL-G / Barman) in production. They handle retention, verification, and parallel restore.

## 14.5 Streaming Replication

### What is it?

A second server (**standby** / replica) continuously receives the **WAL stream** from the main server (**primary**) and replays it. It becomes an almost-live **copy**.

```
 ┌──────────────┐     WAL stream      ┌──────────────┐
 │   PRIMARY    │ ──────────────────► │   STANDBY    │
 │ read + write │                     │  read-only   │
 └──────────────┘                     └──────────────┘
```

### Why use it?

- **High availability (HA):** If the primary fails, **promote** the standby.
- **Read scaling:** Send reports and read-only queries to the standby (`hot_standby = on`).
- **Fast backups:** Take `pg_basebackup` or `pg_dump` from the standby.

### Asynchronous vs synchronous

| | Asynchronous (default) | Synchronous |
|---|---|---|
| Primary waits for standby? | No | **Yes** (before COMMIT returns) |
| Speed | Fast | Slower (network round trip) |
| Data loss if primary dies | Possible (last few transactions) | **None** (for the sync standby) |
| Risk | Replica lag | If the sync standby is down, writes **hang** (use several standbys with `ANY 1 (...)`) |

### Setup, step by step

**Step 1: Configure the primary**

`postgresql.conf`:
```ini
listen_addresses = '*'
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
hot_standby = on                 # allows read queries on the standby
wal_keep_size = 1GB              # extra WAL kept for slow standbys (or use slots)
# archive_mode = on              # optional: keep archiving for PITR too
```

`pg_hba.conf` (allow the standby's IP):
```
host  replication  replicator  10.0.0.12/32  scram-sha-256
```

Create the user and a slot, then reload:
```sql
CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'ReplPass!234';
SELECT pg_create_physical_replication_slot('standby1_slot');
SELECT pg_reload_conf();
```
(Changing `wal_level` or `max_wal_senders` needs a **restart**.)

**Step 2: Build the standby (on the second server)**

Stop PostgreSQL there and make the data directory empty. Then copy from the primary:

```bash
$ sudo systemctl stop postgresql
$ rm -rf /var/lib/postgresql/16/main/*
$ pg_basebackup -h 10.0.0.11 -U replicator \
    -D /var/lib/postgresql/16/main \
    -X stream -R -S standby1_slot -P
$ chown -R postgres:postgres /var/lib/postgresql/16/main
$ sudo systemctl start postgresql
```

`-R` automatically creates:
- an empty file **`standby.signal`** (tells PostgreSQL "start as a standby"), and
- `primary_conninfo` and `primary_slot_name` lines in `postgresql.auto.conf`:
  ```ini
  primary_conninfo = 'host=10.0.0.11 port=5432 user=replicator password=ReplPass!234'
  primary_slot_name = 'standby1_slot'
  ```

**Step 3: Check it works**

On the **primary**:
```sql
SELECT client_addr, state, sync_state,
       sent_lsn, write_lsn, flush_lsn, replay_lsn,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS replay_lag_bytes,
       replay_lag
FROM pg_stat_replication;
```
`state = streaming` means everything is good.

On the **standby**:
```sql
SELECT pg_is_in_recovery();                       -- true on a standby
SELECT * FROM pg_stat_wal_receiver;               -- connection status
SELECT now() - pg_last_xact_replay_timestamp() AS lag;   -- time lag
INSERT INTO products (name, price) VALUES ('x', 1);
-- ERROR: cannot execute INSERT in a read-only transaction
```

**Test:** Insert a row on the primary and `SELECT` it on the standby within a second.

### Replication slots

A **slot** tells the primary: "keep WAL until this standby has received it."

```sql
SELECT slot_name, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM pg_replication_slots;

SELECT pg_drop_replication_slot('standby1_slot');   -- if the standby is gone forever!
```

> **Danger:** An **inactive slot** keeps WAL **forever** and can fill the disk. Always monitor, and set `max_slot_wal_keep_size`.

### Synchronous replication (optional)

On the primary:
```ini
synchronous_standby_names = 'FIRST 1 (standby1, standby2)'    # or 'ANY 1 (standby1, standby2)'
synchronous_commit = on          # or remote_write / remote_apply
```
The standby names come from `application_name` in its `primary_conninfo`.

### Failover (promote a standby)

When the primary is dead:
```bash
$ pg_ctl promote -D /var/lib/postgresql/16/main
# or
$ sudo -u postgres psql -c "SELECT pg_promote();"
```
The standby becomes a normal read-write primary (new timeline). Then:
1. Point your app to the new primary (virtual IP, DNS, or a proxy).
2. **Never** let the old primary come back as a primary (this causes "split brain"). Rebuild it as a new standby, or use `pg_rewind`.

**In production, do not do failover by hand.** Use a tool such as **Patroni**, **repmgr**, or **pg_auto_failover**, or a managed service (AWS RDS/Aurora, Google Cloud SQL, Azure).

### Read-only queries on a standby: conflicts

A long query on the standby can conflict with WAL replay (for example, VACUUM on the primary removed rows the query still needs). Settings:
- `max_standby_streaming_delay` (default 30s): how long replay waits before cancelling the query.
- `hot_standby_feedback = on`: the standby tells the primary which rows it still needs (fewer cancels, but can cause **bloat** on the primary).

### Logical replication (extra: very useful)

Streaming replication copies the **whole cluster**. **Logical replication** copies **chosen tables**, and works across major versions (good for zero-downtime upgrades).

On the **publisher** (`wal_level = logical`):
```sql
CREATE PUBLICATION pub_shop FOR TABLE customers, orders;     -- or FOR ALL TABLES
```

On the **subscriber** (tables must already exist there):
```sql
CREATE SUBSCRIPTION sub_shop
  CONNECTION 'host=10.0.0.11 dbname=shop user=replicator password=...'
  PUBLICATION pub_shop;

SELECT * FROM pg_stat_subscription;
```
Notes: tables need a primary key (or `REPLICA IDENTITY FULL`); DDL (schema changes) and sequences are **not** copied automatically.

| | Streaming (physical) | Logical |
|---|---|---|
| Copies | Everything (byte-level) | Selected tables (row changes) |
| Standby writable? | No | Yes (subscriber can have its own tables) |
| Cross major versions | No | **Yes** |
| Best for | HA, read replicas | Upgrades, data integration, partial copies |

## 14.6 Connection Pooling (PgBouncer and HikariCP)

### Why do we need it?

In PostgreSQL, **each connection is a separate OS process**. It uses memory (about 5-10 MB or more) and CPU. Opening a connection is slow (TCP + login + start process, often 20-100 ms with TLS).

Problems without pooling:
1. Opening and closing a connection for every request is **slow**.
2. Having **thousands** of connections makes PostgreSQL **slower** (context switching, lock contention). More connections ≠ more speed.
3. Many app servers × many threads can easily go over `max_connections`: "FATAL: sorry, too many clients already".

A **pool** keeps a **small set of open connections** and lends them out.

### Two places for pooling

```
 Spring Boot app 1  ─ HikariCP (pool of 10) ─┐
 Spring Boot app 2  ─ HikariCP (pool of 10) ─┼─►  PgBouncer (pool of 20) ─►  PostgreSQL
 Spring Boot app 3  ─ HikariCP (pool of 10) ─┘      (server-side pooler)       (max_connections=100)
   (client-side / application pool)
```

| | HikariCP | PgBouncer |
|---|---|---|
| Where | **Inside your Java app** | A **separate small server** in front of PostgreSQL |
| Pools for | One app instance | **Many apps** together |
| Language | Java only | Any |
| Use it when | Always, in every Java app | You have many app instances, many short-lived clients, serverless, or high connection counts |

Using **both** is common and fine.

---

### PgBouncer

#### Pool modes

| Mode | A server connection is given back to the pool… | Notes |
|---|---|---|
| **session** | when the client **disconnects** | Safest. Least saving. |
| **transaction** | after each **transaction** ends | **Most popular.** Great reuse. But session features break (see below). |
| **statement** | after each **statement** | Very limited (no multi-statement transactions). Rare. |

#### What breaks in transaction mode?

Anything that depends on one session **staying the same** across transactions:
- `SET` (without `LOCAL`), `RESET`, session-level settings
- `LISTEN` / `NOTIFY`
- Session-level advisory locks
- `WITH HOLD` cursors, `PREPARE` statements (older PgBouncer; versions 1.21+ support protocol-level prepared statements with `max_prepared_statements`)
- Temp tables that live across transactions

Use `SET LOCAL` or `set_config(..., true)` inside a transaction instead.

#### Example `pgbouncer.ini`

```ini
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
listen_addr        = 0.0.0.0
listen_port        = 6432
auth_type          = scram-sha-256
auth_file          = /etc/pgbouncer/userlist.txt
admin_users        = pgbouncer_admin
pool_mode          = transaction
max_client_conn    = 1000       ; how many clients can connect to PgBouncer
default_pool_size  = 20         ; server connections per (database, user) pair
min_pool_size      = 5
reserve_pool_size  = 5          ; extra connections for bursts
reserve_pool_timeout = 3
server_idle_timeout  = 600
server_lifetime      = 3600
query_wait_timeout   = 120
max_prepared_statements = 100   ; PgBouncer 1.21+ (prepared statements in transaction mode)
ignore_startup_parameters = extra_float_digits
```

`userlist.txt` holds `"username" "SCRAM-SHA-256$..."` lines. To get the hash:
```sql
SELECT rolname, rolpassword FROM pg_authid WHERE rolname = 'app_user';
```
(Alternative: `auth_query` lets PgBouncer look up passwords itself.)

Run and connect:
```bash
$ pgbouncer -d /etc/pgbouncer/pgbouncer.ini
$ psql -h 127.0.0.1 -p 6432 -U app_user shop        # your app uses port 6432 now
```

Admin console (connect to the special database `pgbouncer`):
```bash
$ psql -h 127.0.0.1 -p 6432 -U pgbouncer_admin pgbouncer
```
```sql
SHOW POOLS;      -- cl_active, cl_waiting (clients waiting = pool too small or queries too slow), sv_active, sv_idle
SHOW STATS;
SHOW CLIENTS;
SHOW SERVERS;
RELOAD;          -- reload config
PAUSE; RESUME;   -- useful for maintenance
```
If `cl_waiting` is often above 0, clients are queuing for a connection.

---

### HikariCP

HikariCP is the **default** connection pool in Spring Boot. It is fast and small.

#### Main settings (Spring Boot `application.yml`)

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/shop
    username: app_user
    password: ${DB_PASSWORD}
    hikari:
      pool-name: ShopPool
      maximum-pool-size: 10          # MOST important setting
      minimum-idle: 10               # best practice: same as max (fixed-size pool)
      connection-timeout: 30000      # ms to wait for a free connection before error
      idle-timeout: 600000           # ms before an idle connection is closed (only if min-idle < max)
      max-lifetime: 1740000          # ms (29 min). MUST be shorter than any DB / PgBouncer / firewall timeout
      keepalive-time: 300000         # ms, ping idle connections (avoid silent drops)
      validation-timeout: 5000
      leak-detection-threshold: 20000   # log a warning if a connection is held > 20 s (finds forgotten close())
```

| Setting | Meaning |
|---|---|
| `maximum-pool-size` | Max connections in the pool (**total**, idle + in use). Default 10. |
| `minimum-idle` | Idle connections to keep. If not set, it equals the max. |
| `connection-timeout` | How long a thread waits for a connection. After that: `SQLTransientConnectionException`. |
| `max-lifetime` | Max age of a connection. Hikari retires it **before** other limits close it. |
| `leak-detection-threshold` | Debug tool for leaks. 0 = off. |

#### How big should the pool be?

**Smaller than you think.** A well-known rule from the HikariCP project:

```
pool size ≈ (number of CPU cores of the DB server × 2) + number of disks
```
For a 4-core DB server, **about 10 connections** can handle thousands of requests per second, if queries are fast. A huge pool just causes queueing **inside** the database (slower for everyone).

Also check: `(number of app instances) × maximum-pool-size ≤ max_connections − reserved` (leave room for admin, monitoring, migrations).

#### Using Hikari with PgBouncer (transaction mode)

- Keep Hikari's pool small and let PgBouncer do the sharing.
- With older PgBouncer versions, turn off server-side prepared statements in the JDBC URL:
  `jdbc:postgresql://pgb-host:6432/shop?prepareThreshold=0`
- Do not use session-level `SET` or advisory locks.
- Flyway migrations should connect **directly** to PostgreSQL (port 5432), not through PgBouncer in transaction mode (Flyway uses session locks).

#### Spot problems

- `HikariPool-1 - Connection is not available, request timed out after 30000ms` → the pool is too small **or** queries are too slow **or** connections are leaking (use `leak-detection-threshold`).
- In PostgreSQL: `SELECT count(*), state FROM pg_stat_activity GROUP BY state;` — many `idle in transaction` = the app opens transactions and does not finish them.

## 14.7 postgresql.conf Tuning

### The config files

| File | Purpose |
|---|---|
| `postgresql.conf` | Main settings |
| `postgresql.auto.conf` | Written by `ALTER SYSTEM`. **Overrides** `postgresql.conf`. Do not edit by hand. |
| `pg_hba.conf` | Who can connect |
| `conf.d/*.conf` | Extra config files (use `include_dir`) |

```sql
SHOW config_file;
SHOW data_directory;
SHOW shared_buffers;
SHOW ALL;
```

### Change settings

```sql
ALTER SYSTEM SET work_mem = '32MB';          -- saved in postgresql.auto.conf
ALTER SYSTEM RESET work_mem;                 -- remove it
SELECT pg_reload_conf();                     -- apply (for settings that don't need a restart)

SET work_mem = '64MB';                       -- only this session
SET LOCAL work_mem = '64MB';                 -- only this transaction
ALTER ROLE report_user SET work_mem = '128MB';        -- default for a role
ALTER DATABASE shop SET random_page_cost = 1.1;       -- default for a database
```

### Which settings need what?

```sql
SELECT name, setting, unit, context, pending_restart
FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'max_connections');
```

| `context` | Meaning |
|---|---|
| `postmaster` | **Restart** needed |
| `sighup` | Reload is enough |
| `superuser` / `user` | Can be changed with `SET` in a session |

`pending_restart = true` means you changed it but still need a restart.

### The most important settings

> Numbers below are **starting points** for a dedicated database server. Change one thing at a time and measure.

#### Memory

| Setting | Default | Suggested start | Explanation |
|---|---|---|---|
| `shared_buffers` | 128MB | **25% of RAM** (e.g. 4GB on a 16GB server) | PostgreSQL's own page cache. Restart needed. |
| `effective_cache_size` | 4GB | **50-75% of RAM** | A *hint* to the planner about how much total cache (PG + OS) exists. Allocates nothing. Higher = more index scans. |
| `work_mem` | 4MB | 16-64MB | Memory **per sort / hash step**, per query, per connection. One query can use several × `work_mem`. Too high × many connections = out-of-memory. |
| `maintenance_work_mem` | 64MB | 512MB-2GB | Used by `VACUUM`, `CREATE INDEX`, `ALTER TABLE ADD FOREIGN KEY`. |
| `autovacuum_work_mem` | -1 (uses above) | 256MB-1GB | Memory for each autovacuum worker. |
| `huge_pages` | try | `try` / `on` | Helps with big `shared_buffers` on Linux. |

**Safe formula for `work_mem`:**
```
work_mem ≈ (RAM − shared_buffers) / (max_connections × 3)      (rough, conservative)
```
Raise it only for specific roles or sessions that need big sorts (reports).

#### Connections

| Setting | Default | Suggested | Explanation |
|---|---|---|---|
| `max_connections` | 100 | 100-300 (use a pooler for more) | Each one costs memory. Restart needed. |
| `superuser_reserved_connections` | 3 | 3 | Keep slots for admins. |
| `idle_in_transaction_session_timeout` | 0 (off) | 5-10min | Kill sessions that wait inside an open transaction (they block VACUUM). |
| `statement_timeout` | 0 (off) | set per role (e.g. 30s for the app) | Stop runaway queries. |
| `lock_timeout` | 0 | e.g. 5s for migrations | Do not wait forever for a lock. |

#### WAL and checkpoints

| Setting | Default | Suggested | Explanation |
|---|---|---|---|
| `max_wal_size` | 1GB | 4-16GB (write-heavy) | Fewer, smoother checkpoints. |
| `min_wal_size` | 80MB | 1-2GB | |
| `checkpoint_timeout` | 5min | 10-15min | Longer = fewer checkpoints (but longer crash recovery). |
| `checkpoint_completion_target` | 0.9 | 0.9 | Spread I/O. |
| `wal_buffers` | -1 (auto) | auto (about 16MB) | |
| `wal_compression` | off | `lz4` / on | Less WAL volume, small CPU cost. |
| `log_checkpoints` | on (PG 15+) | on | See if checkpoints happen too often ("checkpoints are occurring too frequently" warning). |

#### Planner and I/O

| Setting | Default | Suggested | Explanation |
|---|---|---|---|
| `random_page_cost` | 4.0 | **1.1** on SSD/NVMe | Lower = planner likes index scans more. |
| `seq_page_cost` | 1.0 | 1.0 | |
| `effective_io_concurrency` | 1 (16 in some builds) | 200 on SSD | How many parallel I/O requests (bitmap scans). |
| `default_statistics_target` | 100 | 100-500 | Detail of column statistics. |
| `jit` | on | off for pure OLTP | JIT compile helps big analytic queries but can slow short ones. |

#### Parallel query

| Setting | Default | Notes |
|---|---|---|
| `max_worker_processes` | 8 | Total background workers. Restart needed. |
| `max_parallel_workers` | 8 | Workers for parallel queries. |
| `max_parallel_workers_per_gather` | 2 | Workers for one query node. |
| `max_parallel_maintenance_workers` | 2 | For `CREATE INDEX`, `VACUUM`. |

#### Autovacuum (from Phase 4)

`autovacuum_max_workers`, `autovacuum_vacuum_scale_factor`, `autovacuum_vacuum_cost_limit`. Use per-table settings for big tables.

#### Logging (for finding problems)

```ini
logging_collector = on
log_min_duration_statement = 500ms     # log queries slower than 500 ms
log_checkpoints = on
log_connections = on
log_disconnections = on
log_lock_waits = on                    # log waits longer than deadlock_timeout (1s)
log_temp_files = 0                     # log every temp file (sort/hash spill) - find work_mem problems
log_autovacuum_min_duration = 0        # log every autovacuum run
log_line_prefix = '%m [%p] %q%u@%d '
```

#### Extensions to preload

```ini
shared_preload_libraries = 'pg_stat_statements,auto_explain'
pg_stat_statements.track = all
auto_explain.log_min_duration = '1s'
```
(Restart needed.)

```ini

maintenance_work_mem = 1GB

max_wal_size = 8GB
```

### Tuning method (do not guess!)

1. Find **slow queries** first (`pg_stat_statements`, slow log). Most problems are bad queries or missing indexes, **not** config.
2. Set the basic memory settings (above).
3. Watch: cache hit ratio, temp files, checkpoints, connections, locks.
4. Change **one setting at a time**. Measure. Keep notes.
5. Use tools for ideas: **PGTune** (pgtune.leopard.in.ua), **pgBadger** (log reports).

## 14.8 Hands-on: Back Up and Restore a Database

**Goal:** Take a backup of the `shop` database, destroy it, and bring it back. We will do a **logical** backup (pg_dump) and a **physical + PITR-style** exercise (optional).

### Part A: Logical backup and restore (must do)

**Step 1: Make sure there is data**

```sql
SELECT 'customers' AS t, count(*) FROM customers
UNION ALL SELECT 'orders', count(*) FROM orders
UNION ALL SELECT 'products', count(*) FROM products;
```
Write the numbers down.

**Step 2: Back up**

```bash
$ mkdir -p ~/pg_backups
$ pg_dumpall -U postgres --globals-only > ~/pg_backups/globals.sql
$ pg_dump    -U postgres -d shop -Fc -f ~/pg_backups/shop.dump
$ ls -lh ~/pg_backups
```

**Step 3: Check the backup file is readable**

```bash
$ pg_restore -l ~/pg_backups/shop.dump | head -30
```

**Step 4: Simulate a disaster**

```bash
$ psql -U postgres -c "DROP DATABASE shop;"
```
(If you get "database is being accessed by other users", close your other sessions or use `DROP DATABASE shop WITH (FORCE);` in PG 13+.)

**Step 5: Restore**

```bash
$ psql -U postgres -f ~/pg_backups/globals.sql          # roles first (ignore "already exists" errors)
$ createdb -U postgres shop
$ pg_restore -U postgres -d shop -j 4 -v ~/pg_backups/shop.dump
$ psql -U postgres -d shop -c "ANALYZE;"
```

**Step 6: Verify**

Run the count query from Step 1. The numbers must match. Also check:
```sql
\dt
\di
\df
SELECT * FROM audit.audit_log LIMIT 3;     -- the triggers/functions came back too
```

### Part B: Restore a single table (practice)

```bash
$ pg_dump -U postgres -d shop -t public.products -Fc -f ~/pg_backups/products.dump
$ psql -U postgres -d shop -c "DROP TABLE products CASCADE;"      # oops!
$ pg_restore -U postgres -d shop -v ~/pg_backups/products.dump
```
(`CASCADE` also dropped dependent objects, such as foreign keys from other tables. This shows why you should be careful. Restore with a **full** dump if you need those back.)

### Part C: Point-in-time recovery drill (optional, on a test machine)

Follow [14.4 PITR](#144-point-in-time-recovery-pitr):
1. Turn on `archive_mode`.
2. Run `pg_basebackup`.
3. Insert some rows. Note the time. Run `DELETE FROM orders;`.
4. Restore the base backup. Use `recovery_target_time` just before the delete.
5. Verify the rows are back.

### Part D: Backup checklist for real life

- [ ] Backups run **automatically** (cron / systemd timer / pgBackRest).
- [ ] Backups are copied **off the server** (and ideally off-site, encrypted).
- [ ] Roles/globals are backed up too.
- [ ] A **restore test** is done on a schedule (monthly) and the time it takes is known.
- [ ] Monitoring alerts when a backup fails or WAL archiving fails.
- [ ] Retention is defined (for example 7 daily, 4 weekly, 12 monthly).
- [ ] The restore steps are **written down** and others can follow them.

## 14.9 Capstone: Spring Boot + Flyway + Tune the Slowest Query

**Goal:** Build a small Spring Boot app that:
1. Connects to PostgreSQL using **HikariCP**.
2. Uses **Flyway** to create and change the database schema (migrations).
3. Has a **slow endpoint**, which you find with `pg_stat_statements`, analyze with `EXPLAIN (ANALYZE, BUFFERS)`, and **fix** with a new Flyway migration (an index).

You will use almost everything from the 14 days.

### What is Flyway?

**Flyway** is a database **migration tool**. You write SQL files with version numbers. Flyway runs each file **once**, in order, and remembers which ones ran (in a table called `flyway_schema_history`). This gives you **version control for your database**.

```
V1__create_tables.sql     ← runs first
V2__seed_data.sql         ← runs second
V3__add_index.sql         ← runs third
```

**Types of migration files:**

| Prefix | Name example | Meaning |
|---|---|---|
| `V` Versioned | `V3__add_index.sql` | Runs **once**, in version order. |
| `R` Repeatable | `R__refresh_views.sql` | Runs again **whenever its content changes**. Good for views and functions. |
| `U` Undo | `U3__...` | Only in paid editions. |

**Rules:**
- Name pattern: `V<version>__<description>.sql` (**two** underscores).
- **Never edit** a migration that already ran. Flyway stores a **checksum**. If the file changes, `validate` fails. Add a **new** migration instead.
- Keep each migration small and focused.

### Step 7: Find the slowest query

**First, call the endpoints a few times:**
```bash
$ for i in 1 2 3 4 5; do curl -s -o /dev/null -w "%{time_total}s\n" localhost:8080/api/customers/12345/orders; done
$ for i in 1 2 3; do curl -s -o /dev/null -w "%{time_total}s\n" "localhost:8080/api/reports/revenue?status=paid"; done
```

**Now ask PostgreSQL which queries cost the most:**

```sql
SELECT left(query, 80) AS query,
       calls,
       round(total_exec_time::numeric, 1) AS total_ms,
       round(mean_exec_time::numeric, 1)  AS mean_ms,
       rows
FROM pg_stat_statements
WHERE query NOT ILIKE '%pg_stat_statements%'
  AND query NOT ILIKE '%flyway%'
ORDER BY total_exec_time DESC
LIMIT 10;
```

Two ways to rank:
- `ORDER BY total_exec_time DESC` → queries that use the most **total** time (big impact).
- `ORDER BY mean_exec_time DESC` → the slowest **single** runs.

You should see two suspects:
1. `select ... from orders where customer_id = $1 order by created_at desc limit $2` (mean about 50-150 ms: slow for something so simple)
2. The revenue report (mean about 300-800 ms).

Reset the statistics before a new measurement: `SELECT pg_stat_statements_reset();`

### Step 8: Analyze the slow query with EXPLAIN

Take the query from the app (replace `$1`) and run it **inside a transaction** (good habit):

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 12345
ORDER BY created_at DESC
LIMIT 20;
```

**What you will probably see (example):**
```
Limit  (cost=40000..40000 rows=20) (actual time=95.1..95.2 rows=20 loops=1)
  -> Gather Merge
       -> Sort  (Sort Key: created_at DESC, Sort Method: top-N heapsort)
            -> Parallel Seq Scan on orders
                 Filter: (customer_id = 12345)
                 Rows Removed by Filter: 666650
Execution Time: 96.0 ms
```

**Diagnosis (use Day 11 skills):**
- `Seq Scan` on 2M rows to return about 10 rows.
- Huge `Rows Removed by Filter`.
- Cause: **no index on `customer_id`** (foreign keys are not indexed automatically).

### Step 9: Fix it with a new Flyway migration

**Never** edit `V1`. Create `V3__add_orders_index.sql`:

```sql
-- Matches the query: filter on customer_id, sort by created_at DESC
CREATE INDEX idx_orders_customer_created
  ON orders (customer_id, created_at DESC);
```

**Production note:** `CREATE INDEX` blocks writes while it builds. For a live system use `CONCURRENTLY`. But it cannot run inside a transaction, and Flyway wraps each migration in one by default. Fix with a config file next to the migration:

`V3__add_orders_index.sql`:
```sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_customer_created
  ON orders (customer_id, created_at DESC);
```
`V3__add_orders_index.sql.conf`:
```properties
executeInTransaction=false
```
(Flyway reads a `.conf` file with the same name as the migration. Keep **only one statement** in a non-transactional migration, so a failure cannot leave you half-done.)

Restart the app. Flyway applies V3. Then:

```sql
ANALYZE orders;

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE customer_id = 12345
ORDER BY created_at DESC
LIMIT 20;
```

**Expected:**
```
Limit  (actual time=0.03..0.05 rows=10 loops=1)
  -> Index Scan using idx_orders_customer_created on orders
       Index Cond: (customer_id = 12345)
Execution Time: 0.07 ms
```
No `Sort` node. About **1000× faster**.

### Step 10: Tune the second slow query (the report)

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.country, count(*) AS orders, sum(o.amount) AS revenue
FROM orders o JOIN customers c ON c.id = o.customer_id
WHERE o.status = 'paid'
GROUP BY c.country
ORDER BY revenue DESC;
```

You will likely see `Hash Join` + two `Seq Scan` nodes + `HashAggregate`. About a quarter of the 2M rows match (`status = 'paid'`), so a seq scan is **correct** here. An index on `status` will not help (low selectivity). Options:

| Option | How | Use when |
|---|---|---|
| Check for disk spills | Look for `Batches > 1` or `Disk:` | Then raise `work_mem` for this query: `SET LOCAL work_mem = '64MB'` |
| Covering index | `CREATE INDEX ON orders (status) INCLUDE (customer_id, amount);` → Index Only Scan (run `VACUUM` first) | The query is frequent and you want to avoid reading the table |
| **Materialized view** | Pre-compute and refresh every few minutes | The report is heavy and "a few minutes old" is OK (**best here**) |
| Parallel workers | `max_parallel_workers_per_gather` | CPU is idle |

Using a **materialized view** in a Flyway **versioned** migration `V4__revenue_mv.sql`:

```sql
CREATE MATERIALIZED VIEW mv_revenue_by_country_status AS
SELECT c.country, o.status, count(*) AS orders, sum(o.amount) AS revenue
FROM orders o
JOIN customers c ON c.id = o.customer_id
GROUP BY c.country, o.status;

CREATE UNIQUE INDEX ON mv_revenue_by_country_status (country, status);
```

Then change the repository query to read from it:

```java
@Query(value = """
    SELECT country AS country, orders AS orders, revenue AS revenue
    FROM mv_revenue_by_country_status
    WHERE status = :status
    ORDER BY revenue DESC
    """, nativeQuery = true)
List<CountryRevenue> revenueByCountry(@Param("status") String status);
```

And refresh it on a schedule (add `@EnableScheduling` to the application class):

```java
@Component
class RevenueRefresher {
    private final JdbcTemplate jdbc;
    RevenueRefresher(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Scheduled(fixedDelay = 300_000)      // every 5 minutes
    void refresh() {
        jdbc.execute("REFRESH MATERIALIZED VIEW CONCURRENTLY mv_revenue_by_country_status");
    }
}
```
(`JdbcTemplate` is in `spring-boot-starter-jdbc`, which `spring-boot-starter-data-jpa` already includes.)

Now the report takes about 1 ms.

### Flyway: useful commands and troubleshooting

You can run Flyway from Maven, Gradle, CLI, or Spring Boot on startup. With the Maven plugin (`flyway-maven-plugin`):

```bash
$ mvn flyway:info        # show which migrations ran / are pending
$ mvn flyway:migrate     # apply pending migrations
$ mvn flyway:validate    # check checksums
$ mvn flyway:repair      # remove failed entries, realign checksums
$ mvn flyway:baseline    # mark an existing database as version N
```

| Problem | Meaning | Fix |
|---|---|---|
| `Validate failed: Migration checksum mismatch` | Someone edited an applied migration | Revert the file. Add a new migration. (Only if the change is harmless: `flyway repair`.) |
| `Detected failed migration to version X` | A migration failed halfway | PostgreSQL can roll back DDL, so usually the transaction is rolled back. Fix the SQL, run `repair`, retry. (Non-transactional migrations like `CONCURRENTLY` can leave an INVALID index: drop it first.) |
| `Found non-empty schema(s) but no schema history table` | You added Flyway to an existing database | Set `baseline-on-migrate: true` (and `baseline-version`) once, or run `baseline`. |
| `Detected resolved migration not applied ... out of order` | You added `V2` after `V3` ran | Use `spring.flyway.out-of-order=true` (carefully) or renumber. |
| Two app instances start together | Flyway takes a **lock**, so one waits | This is normal and safe. |

**Good Flyway habits:**
- One change per migration. Small files.
- Use `IF NOT EXISTS` / `IF EXISTS` where it makes sense.
- Never edit applied migrations.
- Test migrations on a **copy of production data** (a restored backup is perfect).
- Set `lock_timeout` in risky DDL: `SET lock_timeout = '5s';` so a migration fails fast rather than blocking the whole app.
- For big tables: add columns with defaults (fast in PG 11+), create indexes `CONCURRENTLY`, and backfill data in batches.

# Final Cheat Sheet

## Programmability

```sql
-- View
CREATE OR REPLACE VIEW v AS SELECT ...;
-- Materialized view
CREATE MATERIALIZED VIEW mv AS SELECT ... ;
CREATE UNIQUE INDEX ON mv (col);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv;
-- Function
CREATE OR REPLACE FUNCTION f(a int) RETURNS int LANGUAGE sql IMMUTABLE AS $$ SELECT a + 1 $$;
-- Procedure
CREATE PROCEDURE p() LANGUAGE plpgsql AS $$ BEGIN ... COMMIT; END $$;  CALL p();
-- Trigger
CREATE FUNCTION t() RETURNS trigger LANGUAGE plpgsql AS $$ BEGIN RETURN NEW; END $$;
CREATE TRIGGER trg BEFORE INSERT OR UPDATE ON tbl FOR EACH ROW EXECUTE FUNCTION t();
```

| I want to… | Use |
|---|---|
| Reuse a query / hide columns | **View** |
| Speed up a heavy report (stale OK) | **Materialized view** |
| Return a value / use in `SELECT` or index | **Function** |
| Multi-step job with commits | **Procedure** + `CALL` |
| React automatically to changes | **Trigger** |
| Allow a view to be edited when complex | `INSTEAD OF` trigger |

## Security

```sql
CREATE ROLE grp NOLOGIN;  CREATE ROLE usr LOGIN PASSWORD '...';  GRANT grp TO usr;
GRANT CONNECT ON DATABASE db TO grp;
GRANT USAGE ON SCHEMA public TO grp;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO grp;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO grp;
ALTER TABLE t ENABLE ROW LEVEL SECURITY;  ALTER TABLE t FORCE ROW LEVEL SECURITY;
CREATE POLICY p ON t USING (tenant_id = current_setting('app.tenant_id')::int);
```

## Full-text search

```sql
ALTER TABLE a ADD COLUMN search tsvector GENERATED ALWAYS AS (to_tsvector('english', title || ' ' || body)) STORED;
CREATE INDEX ON a USING gin (search);
SELECT * FROM a WHERE search @@ websearch_to_tsquery('english', 'my search');
```

## Backup and recovery

| Task | Command |
|---|---|
| Logical backup (custom) | `pg_dump -U u -d db -Fc -f db.dump` |
| Parallel logical backup | `pg_dump -d db -Fd -j 4 -f dir` |
| Roles backup | `pg_dumpall --globals-only > globals.sql` |
| Restore | `pg_restore -d newdb -j 4 db.dump` |
| Physical backup | `pg_basebackup -D dir -Ft -z -X stream -P` |
| PITR | base backup + `restore_command` + `recovery_target_time` + `recovery.signal` |
| Build standby | `pg_basebackup -R -S slot -D dir` (creates `standby.signal`) |
| Promote standby | `pg_ctl promote` or `SELECT pg_promote();` |

## Pooling

| Layer | Tip |
|---|---|
| HikariCP | Small pool (about 10), `max-lifetime` < DB/proxy timeouts, use `leak-detection-threshold` |
| PgBouncer | `pool_mode = transaction`, avoid session features, run migrations on a direct connection |
| PostgreSQL | `max_connections` ≥ apps × pool size + admin slots |

## Config quick start (16 GB RAM, SSD)

`shared_buffers=4GB`, `effective_cache_size=12GB`, `work_mem=16MB`, `maintenance_work_mem=1GB`, `random_page_cost=1.1`, `max_wal_size=8GB`, `checkpoint_timeout=15min`, `log_min_duration_statement=500ms`, `shared_preload_libraries='pg_stat_statements'`.
