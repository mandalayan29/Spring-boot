# Day 10: Indexes

## 10.1 What is an index?

Think of a book. If you want to find the word "vacuum", you have two choices:

1. Read every page from page 1 (slow).
2. Open the **index** at the back, find "vacuum → page 245", and go to that page (fast).

A database index works the same way. It is a **separate data structure** that helps PostgreSQL find rows without reading the whole table.

**Without an index:** PostgreSQL does a **Sequential Scan** (reads every row).
**With an index:** PostgreSQL can do an **Index Scan** (jumps to the right rows).

### The trade-off (very important)

| Good | Bad |
|---|---|
| `SELECT` queries get much faster | `INSERT`, `UPDATE`, `DELETE` get slower (the index must be updated too) |
| Sorting and `ORDER BY` can be faster | Indexes use disk space |
| `UNIQUE` rules can be enforced | Too many indexes = slow writes + wasted space |

**Rule:** Do not add indexes everywhere. Add them where queries need them.

---

## 10.2 Basic syntax

```sql
-- Create an index
CREATE INDEX index_name ON table_name (column_name);

-- Create with a specific type
CREATE INDEX index_name ON table_name USING btree (column_name);

-- Unique index
CREATE UNIQUE INDEX index_name ON table_name (column_name);

-- Create without blocking writes (safe for production)
CREATE INDEX CONCURRENTLY index_name ON table_name (column_name);

-- Only create if it does not exist
CREATE INDEX IF NOT EXISTS index_name ON table_name (column_name);

-- Drop an index
DROP INDEX index_name;
DROP INDEX CONCURRENTLY index_name;

-- Rebuild an index (fixes bloat)
REINDEX INDEX index_name;
REINDEX TABLE table_name;
REINDEX INDEX CONCURRENTLY index_name;   -- PostgreSQL 12+
```

**Notes:**
- A `PRIMARY KEY` or `UNIQUE` constraint automatically creates a B-tree index.
- `CREATE INDEX` (normal) blocks writes (`INSERT/UPDATE/DELETE`) on the table while it builds. `CONCURRENTLY` does not block writes, but it is slower and cannot run inside a transaction block.
- If `CREATE INDEX CONCURRENTLY` fails, it can leave an **INVALID** index behind. Drop it and try again.

---

## 10.3 Index types

### 10.3.1 B-tree (the default)

**What it is:** A balanced tree. Data is kept **sorted**. PostgreSQL walks from the top of the tree down to the leaf, like finding a name in a sorted phone book.

**Good for:**
- Equality: `=`
- Range: `<`, `<=`, `>`, `>=`, `BETWEEN`
- Sorting: `ORDER BY`
- `IS NULL` / `IS NOT NULL`
- Prefix search: `LIKE 'abc%'` (with some conditions, see below)
- `MIN()` and `MAX()`

**Syntax:**
```sql
CREATE INDEX idx_customers_email ON customers (email);
-- same as:
CREATE INDEX idx_customers_email ON customers USING btree (email);
```

**Example queries that use it:**
```sql
SELECT * FROM customers WHERE email = 'user500@example.com';
SELECT * FROM customers WHERE created_at >= '2026-01-01';
SELECT * FROM customers ORDER BY created_at DESC LIMIT 10;
```

**Sort order options:**
```sql
CREATE INDEX idx_c_created_desc ON customers (created_at DESC);
CREATE INDEX idx_c_balance ON customers (balance ASC NULLS LAST);
```
For a single column, B-tree can be read forward or backward, so `DESC` is not needed for single-column sorting. It matters in **multi-column** indexes with mixed directions, like `ORDER BY a ASC, b DESC`.

**The `LIKE 'abc%'` detail:** A normal B-tree can help `LIKE 'abc%'` only if the database uses the `C` collation. Most databases don't. Use an operator class:

```sql
CREATE INDEX idx_c_email_pattern ON customers (email text_pattern_ops);

SELECT * FROM customers WHERE email LIKE 'user5%';   -- can use index
```
`LIKE '%abc'` or `LIKE '%abc%'` (wildcard at the start) can **not** use a B-tree. Use `pg_trgm` + GIN (see below).

**When to use:** Almost always. If you are not sure, use B-tree.

---

### 10.3.2 Hash

**What it is:** Uses a hash function. It turns the value into a number and jumps to a "bucket".

**Good for:** Equality (`=`) **only**.
**Not good for:** Ranges, sorting, `LIKE`.

**Syntax:**
```sql
CREATE INDEX idx_c_email_hash ON customers USING hash (email);
```

**Example:**
```sql
SELECT * FROM customers WHERE email = 'user500@example.com';
```

**When to use:**
- You only ever do `=` lookups on a long value (long text, URLs, tokens).
- The index can be smaller than a B-tree for long values.

**When NOT to use:**
- You may need `<`, `>`, or `ORDER BY` later.
- Hash indexes cannot be `UNIQUE`.
- They support only **one column**.

> In practice, B-tree is good enough for most equality searches, so Hash is rarely needed. Since PostgreSQL 10, Hash indexes are crash-safe and WAL-logged.

---

### 10.3.3 GIN (Generalized Inverted Index)

**What it is:** An "inverted index". Think of the index at the back of a book: for every **word**, it stores the **list of pages**. GIN does the same: for every **element** inside a value (array item, JSON key, word), it stores the list of rows that contain it.

**Good for:**
- **JSONB**: `@>`, `?`, `?|`, `?&`
- **Arrays**: `@>`, `<@`, `&&`
- **Full-text search**: `@@`
- **Fuzzy / substring text search** with `pg_trgm`: `LIKE '%abc%'`, `ILIKE`

**Syntax:**
```sql
CREATE INDEX idx_c_tags ON customers USING gin (tags);
CREATE INDEX idx_c_profile ON customers USING gin (profile);
```

**Example: arrays**
```sql
-- rows whose tags array contains 'vip'
SELECT * FROM customers WHERE tags @> ARRAY['vip'];

-- rows whose tags overlap with any of these
SELECT * FROM customers WHERE tags && ARRAY['vip','beta'];
```

**Example: JSONB**
```sql
-- rows where profile contains {"plan": "pro"}
SELECT * FROM customers WHERE profile @> '{"plan": "pro"}';

-- rows that have the key "age"
SELECT * FROM customers WHERE profile ? 'age';
```

**Smaller, faster JSONB index (`jsonb_path_ops`):**
```sql
CREATE INDEX idx_c_profile_path ON customers USING gin (profile jsonb_path_ops);
```
- It supports only `@>` (and a few JSON path operators), but it is smaller and faster.
- The default `jsonb_ops` supports more operators (`?`, `?|`, `?&`).

**Example: full-text search**
```sql
CREATE INDEX idx_articles_fts
ON articles USING gin (to_tsvector('english', title || ' ' || body));

SELECT * FROM articles
WHERE to_tsvector('english', title || ' ' || body) @@ to_tsquery('english', 'postgres & index');
```
> The expression in the query must match the expression in the index exactly.

**Example: substring search with `pg_trgm`**
```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_c_email_trgm ON customers USING gin (email gin_trgm_ops);

SELECT * FROM customers WHERE email ILIKE '%user99%';   -- can use index now
```

**When to use:** Values that contain many items (arrays, JSON, text).
**Trade-offs:** GIN indexes are **slow to update** and can be big. PostgreSQL uses a "pending list" (`fastupdate`) to speed up writes a little.

---

### 10.3.4 GiST (Generalized Search Tree)

**What it is:** A flexible tree for data that has "shape" or "closeness", not just order.

**Good for:**
- **Geometry**: points, boxes, polygons (and PostGIS)
- **Range types**: `int4range`, `tstzrange`, `daterange` with `&&`, `@>`, `<@`
- **Nearest-neighbor search**: `ORDER BY column <-> point LIMIT n`
- **Exclusion constraints**: "no two bookings may overlap"
- Full-text search (GIN is usually better for reading)

**Syntax:**
```sql
CREATE INDEX idx_places_location ON places USING gist (location);
```

**Example: nearest neighbor**
```sql
CREATE TABLE places (id serial PRIMARY KEY, name text, location point);
CREATE INDEX idx_places_loc ON places USING gist (location);

-- 5 closest places to point (10, 20)
SELECT name FROM places
ORDER BY location <-> point '(10,20)'
LIMIT 5;
```

**Example: overlapping time ranges**
```sql
CREATE TABLE room_bookings (
  id serial PRIMARY KEY,
  room_id int,
  period tstzrange
);

CREATE INDEX idx_bookings_period ON room_bookings USING gist (period);

-- Which bookings overlap this time?
SELECT * FROM room_bookings
WHERE period && tstzrange('2026-11-01 10:00', '2026-11-01 12:00');
```

**Example: stop double-booking (exclusion constraint)**
```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE room_bookings
ADD CONSTRAINT no_overlap
EXCLUDE USING gist (room_id WITH =, period WITH &&);
```
This says: "same room AND overlapping time = not allowed." `btree_gist` is needed so GiST can handle the plain `=` on `room_id`.

**GIN vs GiST (quick):**
| | GIN | GiST |
|---|---|---|
| Read speed | Faster | Slower |
| Write speed | Slower | Faster |
| Size | Bigger | Smaller |
| Best for | Arrays, JSONB, FTS | Geometry, ranges, nearest-neighbor |

---

### 10.3.5 BRIN (Block Range Index)

**What it is:** A tiny index. Instead of storing every value, it stores the **min and max value for each group of pages** (a "block range", default 128 pages). During a query, PostgreSQL skips block ranges that cannot match.

**Works only if** the column's values are **naturally ordered** on disk, for example:
- Log tables where `created_at` always increases
- Time-series sensor data
- Auto-increment IDs on append-only tables

**Syntax:**
```sql
CREATE INDEX idx_logs_created_brin ON logs USING brin (created_at);

-- with a smaller range = more precise, a bit bigger
CREATE INDEX idx_logs_created_brin2 ON logs USING brin (created_at) WITH (pages_per_range = 32);
```

**Example:**
```sql
SELECT count(*) FROM logs
WHERE created_at >= '2026-10-01' AND created_at < '2026-10-02';
```

**Check if BRIN will work (correlation):**
```sql
SELECT attname, correlation
FROM pg_stats
WHERE tablename = 'logs' AND attname = 'created_at';
```
`correlation` close to **1** (or **-1**) = good for BRIN. Close to **0** = random order = BRIN is useless.

**Why it's special:** On a 100 GB table, a B-tree might be 20 GB. A BRIN index might be **a few MB**.

**When NOT to use:** Randomly ordered data, or tables with many updates and deletes that scatter the order.

| Index | Equality `=` | Range `< >` | Sorting | Arrays/JSON/Text | Geometry/Nearest | Size |

| B-tree | ✅ | ✅ | ✅ | ❌ | ❌ | Medium |
| Hash | ✅ | ❌ | ❌ | ❌ | ❌ | Small–Medium |
| GIN | ✅ (element) | ❌ | ❌ | ✅ | ❌ | Large |
| GiST | ✅ | ✅ (ranges) | ❌ (except distance) | Partial | ✅ | Medium |
| BRIN | ✅ | ✅ | ❌ | ❌ | ❌ | Tiny |

## 10.4 Special index kinds

### 10.4.1 Composite (multi-column) indexes

**What it is:** One index on **more than one column**.

**Syntax:**
```sql
CREATE INDEX idx_c_country_status ON customers (country, status);
```

**The golden rule: leftmost prefix.**
The index is sorted by the **first column**, then the second inside it, and so on (like a phone book sorted by last name, then first name).

For index `(country, status, created_at)`:

| Query filter | Uses the index well? |
|---|---|
| `country = 'IN'` | ✅ Yes |
| `country = 'IN' AND status = 'active'` | ✅ Yes |
| `country = 'IN' AND status = 'active' AND created_at > ...` | ✅ Yes (best) |
| `status = 'active'` | ❌ Poor (skips first column) |
| `created_at > ...` | ❌ Poor |
| `country = 'IN' AND created_at > ...` | ⚠️ Partly (uses `country` only for fast narrowing; `created_at` is filtered inside that range) |

> PostgreSQL 18 added "skip scan" for some of these cases, but do not depend on it. Design for the leftmost-prefix rule.

**Column order guideline:**
1. Columns used with `=` first.
2. Then the column used with a range (`>`, `<`, `BETWEEN`) or `ORDER BY`.
3. Among equality columns, put the more selective one (fewer matching rows) first, but also think about which queries you run most.

**Example:**
```sql
-- Query:
SELECT * FROM customers
WHERE country = 'IN' AND status = 'active'
ORDER BY created_at DESC
LIMIT 20;

-- Best index:
CREATE INDEX idx_c_country_status_created
ON customers (country, status, created_at DESC);
```
This index finds the right rows **already sorted**, so no extra sort step is needed.

**When to use:** Queries that filter or sort on the same group of columns again and again.
**Tip:** Do not create `(a)` **and** `(a, b)`. The second one already covers queries on `a`. Drop `(a)`.
**Limit:** B-tree supports up to 32 columns, but 2–4 is typical.

---

### 10.4.2 Partial indexes

**What it is:** An index on **only some rows**, defined with `WHERE`.

**Syntax:**
```sql
CREATE INDEX index_name ON table_name (column) WHERE condition;
```

**Example 1: Rare rows**
Only 2% of customers are `blocked`, and you often look for them.
```sql
CREATE INDEX idx_c_blocked ON customers (created_at) WHERE status = 'blocked';

SELECT * FROM customers
WHERE status = 'blocked' AND created_at > '2026-01-01';   -- uses the small index
```

**Example 2: Unique rule only for active rows (soft delete)**
```sql
CREATE UNIQUE INDEX uq_users_email_active
ON users (email) WHERE deleted_at IS NULL;
```
Now two *deleted* users can have the same email, but two *active* users cannot.

**Important rule:** The query's `WHERE` must clearly **imply** the index's `WHERE`. If your index has `WHERE status = 'blocked'`, then your query must also contain `status = 'blocked'`. PostgreSQL does not guess.

**When to use:**
- The queries only care about a small part of the table (pending jobs, unpaid invoices, active rows).
- You want a smaller, faster index.
- You need a "conditional unique" rule.

---

### 10.4.3 Covering indexes (`INCLUDE`)

**Background:** Normally an index finds the row location, then PostgreSQL goes to the **table (heap)** to get the other columns. That extra trip costs time.

**Index-Only Scan:** If the index contains **all columns the query needs**, PostgreSQL can answer from the index alone, with no table visit.

**Syntax (PostgreSQL 11+):**
```sql
CREATE INDEX index_name ON table_name (key_columns) INCLUDE (extra_columns);
```

**Example:**
```sql
-- Query:
SELECT customer_id, amount FROM orders WHERE customer_id = 42;

-- Covering index:
CREATE INDEX idx_orders_cust_incl
ON orders (customer_id) INCLUDE (amount);
```
- `customer_id` is the **search key** (used to find rows).
- `amount` is **payload** (just stored in the index so it can be returned).

**Why not just `(customer_id, amount)`?**
- `INCLUDE` columns are not used for ordering or searching, and they do not need a sortable type.
- It keeps the upper tree levels smaller.
- A unique index can be unique on the key only: `CREATE UNIQUE INDEX ... (email) INCLUDE (name)`.

**Very important: the Visibility Map.**
Index-only scans need the table's **visibility map** to be up to date. That is maintained by `VACUUM`. In `EXPLAIN ANALYZE`, look for `Heap Fetches: 0`. If this number is large, run `VACUUM table_name;`.

**When to use:** A hot query reads a few columns and you want to avoid table lookups.
**When NOT to use:** Don't include big columns (long text). Don't include everything. The index will become huge.

---

### 10.4.4 Expression indexes (functional indexes)

**What it is:** An index on the **result of a function or expression**, not on the raw column.

**Syntax:**
```sql
CREATE INDEX index_name ON table_name ((expression));
```
Note the **double parentheses** for expressions (not needed for a simple function call, but it is a good habit).

**The problem it solves:**
```sql
-- Index on email exists, but this query CAN'T use it:
SELECT * FROM customers WHERE lower(email) = 'user500@example.com';
```
The index stores `email`, not `lower(email)`. They are different, so PostgreSQL ignores the index.

**The fix:**
```sql
CREATE INDEX idx_c_lower_email ON customers (lower(email));

SELECT * FROM customers WHERE lower(email) = 'user500@example.com';   -- now fast
```

**More examples:**
```sql
-- Search by date part of a timestamp
CREATE INDEX idx_c_created_date ON customers ((created_at::date));
SELECT * FROM customers WHERE created_at::date = '2026-05-10';

-- Search inside JSONB
CREATE INDEX idx_c_plan ON customers ((profile->>'plan'));
SELECT * FROM customers WHERE profile->>'plan' = 'pro';

-- Computed value
CREATE INDEX idx_c_len_email ON customers ((length(email)));
```

**Rules:**
- The function must be **IMMUTABLE** (same input always gives the same output). `now()` or `random()` are not allowed.
- The query must use the **exact same expression**.
- After creating an expression index, run `ANALYZE table_name;` so PostgreSQL collects statistics on that expression.
- Writes are slower because the function runs on every insert/update.

---

### 10.4.5 Unique and multi-purpose notes

```sql
CREATE UNIQUE INDEX uq_c_email ON customers (email);          -- enforce uniqueness
ALTER TABLE customers ADD CONSTRAINT uq_c_email UNIQUE (email); -- same effect, as a constraint
```

Combine features. All of these are legal:
```sql
CREATE UNIQUE INDEX uq_active_email ON users (lower(email)) WHERE deleted_at IS NULL;
CREATE INDEX idx_o_cust ON orders (customer_id, order_date DESC) INCLUDE (amount) WHERE status = 'paid';
```

## 10.5 When does PostgreSQL NOT use my index?

Don't panic. This is normal. Common reasons:

1. **The table is small.** Reading the whole table is cheaper than using the index.
2. **The query returns a big part of the table** (for example, 30%+ of rows). A seq scan is faster.
3. **A function or cast on the column**: `WHERE lower(email) = ...`, `WHERE created_at::date = ...`, `WHERE id + 1 = 5`. Use an expression index or rewrite: `created_at >= '2026-05-10' AND created_at < '2026-05-11'`.
4. **Type mismatch** (for example comparing an `int` column to a `numeric`/`text` in a way that forces a cast).
5. **Leading wildcard**: `LIKE '%abc'`.
6. **Wrong column order** in a composite index.
7. **Old statistics.** Run `ANALYZE`.
8. **`OR` conditions** on different columns (may use a Bitmap OR, but not always).
9. **The index does not match the query's operator** (for example, B-tree for `@>` on JSONB).

## 10.6 Index maintenance and useful queries

**List indexes on a table:**
```sql
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'customers';
```
or in `psql`: `\d customers`

**Index and table sizes:**
```sql
SELECT pg_size_pretty(pg_relation_size('customers'))         AS table_size,
       pg_size_pretty(pg_indexes_size('customers'))          AS all_indexes_size,
       pg_size_pretty(pg_total_relation_size('customers'))   AS total_size;

SELECT indexrelname, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes WHERE relname = 'customers';
```

**Find unused indexes** (after the system has run for a while):
```sql
SELECT schemaname, relname AS table_name, indexrelname AS index_name,
       idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```
`idx_scan = 0` means the index was never used since statistics were last reset. (Do not drop indexes that back a `PRIMARY KEY`/`UNIQUE` constraint.)

**Find duplicate-looking indexes:** Look at `indexdef` for identical column lists.

## 10.7 Hands-on (Day 10): Generate 1M rows and measure

### Step 1: Create the table

```sql
DROP TABLE IF EXISTS customers;

CREATE TABLE customers (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email       text         NOT NULL,
  country     text         NOT NULL,
  status      text         NOT NULL,
  created_at  timestamptz  NOT NULL,
  balance     numeric(10,2) NOT NULL,
  tags        text[],
  profile     jsonb
);
```

### Step 2: Insert 1,000,000 rows

```sql
INSERT INTO customers (email, country, status, created_at, balance, tags, profile)
SELECT
  'user' || g || '@example.com',
  (ARRAY['IN','US','UK','DE','FR','BR','JP','CA'])[1 + (random()*7)::int],
  CASE WHEN random() < 0.02 THEN 'blocked'
       WHEN random() < 0.30 THEN 'inactive'
       ELSE 'active' END,
  now() - random() * interval '730 days',
  round((random() * 10000)::numeric, 2),
  ARRAY[(ARRAY['vip','new','promo','beta'])[1 + (random()*3)::int]],

    'plan', (ARRAY['free','pro','team'])[1 + (random()*2)::int],
    'age',  18 + (random()*50)::int
  )
FROM generate_series(1, 1000000) AS g;

ANALYZE customers;   -- ALWAYS update statistics after a big load
```

What `generate_series(1, 1000000)` does: it creates a list of numbers 1 to 1,000,000. For each number, we build one fake row.

Check the size:
```sql
SELECT pg_size_pretty(pg_total_relation_size('customers'));
```

### Step 3: Turn on timing

In `psql`:
```sql
\timing on
```

### Step 4: Measure BEFORE indexes

Run each query **twice** (the first run may be slower because data is not in memory yet). Note the time of the second run.

```sql

-- Q2: filter + sort + limit

EXPLAIN (ANALYZE, BUFFERS)

EXPLAIN (ANALYZE, BUFFERS)
```

```sql

-- Q2 (composite, equality first, then sort column)

```

### Step 6: Measure AFTER indexes

Run the same 7 queries again. Compare the times.

**Typical results (example only):**

| Query | Before | After |
|---|---|---|

| Q2 country+status sort | ~150 ms | ~0.1 ms |
| Q3 blocked count | ~80 ms | ~5 ms |
| Q4 array contains | ~120 ms | ~40 ms |
| Q6 lower(email) | ~100 ms | ~0.05 ms |


# Day 11: Query Planning

## 11.1 What is a query planner?

When you send a SQL query, PostgreSQL does **not** run it directly. It does these steps:

1. **Parse**: check the syntax.
2. **Rewrite**: expand views and rules.
3. **Plan (optimize)**: the **planner** creates many possible ways to run the query and **estimates the cost** of each one. It picks the cheapest.
4. **Execute**: run the chosen plan.

The planner makes **estimates** using **statistics** about your tables. If the statistics are wrong or old, the plan can be bad. This is the cause of many slow queries.

## 11.2 EXPLAIN: see the plan

### Syntax

```sql
EXPLAIN query;                           -- shows the plan only (does NOT run the query)
EXPLAIN ANALYZE query;                   -- RUNS the query and shows real times
EXPLAIN (ANALYZE, BUFFERS) query;        -- also shows memory/disk block usage
EXPLAIN (ANALYZE, BUFFERS, VERBOSE) query;
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) query;   -- for tools (e.g., explain.dalibo.com)
EXPLAIN (ANALYZE, TIMING OFF) query;     -- less overhead on very fast nodes
EXPLAIN (ANALYZE, BUFFERS, SETTINGS) query; -- shows non-default settings (PG 12+)
```

> ⚠️ **`EXPLAIN ANALYZE` really runs the query.** For `INSERT`, `UPDATE`, `DELETE`, it **changes data**. Always wrap it:
> ```sql
> BEGIN;
> EXPLAIN ANALYZE UPDATE customers SET balance = 0 WHERE country = 'IN';
> ROLLBACK;
> ```

### Basic example

```sql
EXPLAIN SELECT * FROM customers WHERE id = 500;
```
```
Index Scan using customers_pkey on customers  (cost=0.42..8.44 rows=1 width=120)
  Index Cond: (id = 500)
```

### How to read one line

```
Seq Scan on customers  (cost=0.00..25000.00 rows=1000000 width=120) (actual time=0.02..120.5 rows=1000000 loops=1)
```

| Part | Meaning |
|---|---|
| `Seq Scan on customers` | The **node type** and the table |
| `cost=0.00..25000.00` | `startup cost .. total cost`. Startup = work before the first row can be returned. Total = work for all rows. The unit is **arbitrary** (not milliseconds). Use it only to compare plans. |
| `rows=1000000` | **Estimated** number of rows this node returns |
| `width=120` | Estimated average row size in bytes |
| `actual time=0.02..120.5` | **Real** time in ms: first row .. last row (only with `ANALYZE`) |
| `rows=1000000` (in actual) | **Real** number of rows |
| `loops=1` | How many times this node ran. **Multiply** time and rows by loops to get totals. |

### How to read the whole plan

A plan is a **tree**. Indentation shows the parent/child relation. Read it from the **innermost / most indented** nodes (they run first) outward to the top.

```
Sort
  -> Hash Join
       -> Seq Scan on orders
       -> Hash
            -> Seq Scan on customers
```
Order: scan `customers` → build `Hash` → scan `orders` → `Hash Join` → `Sort`.

### Extra lines to watch

| Line | Meaning |
|---|---|
| `Filter: (...)` | Rows are read, then thrown away if they don't match. |
| `Rows Removed by Filter: 999000` | A big number = you read much and kept little = probably needs an index. |
| `Index Cond: (...)` | The condition was used **inside** the index (good). |
| `Heap Fetches: N` | Index-only scan had to visit the table N times. High = run `VACUUM`. |
| `Sort Method: quicksort Memory: 25kB` | Sort fit in memory (good). |
| `Sort Method: external merge Disk: 80000kB` | Sort spilled to disk (slow). Raise `work_mem` or add an index. |
| `Batches: 8` (in Hash) | The hash table didn't fit in `work_mem`; it used disk. |
| `Planning Time` / `Execution Time` | Time to make the plan / time to run it. |
| `Buffers: shared hit=... read=...` | See below. |

### BUFFERS explained

```
Buffers: shared hit=120 read=3500 dirtied=0 written=0
```
Every "buffer" is one 8 KB block.

| Item | Meaning |
|---|---|
| `shared hit` | Blocks found in PostgreSQL's memory cache (fast) |
| `shared read` | Blocks read from disk / OS cache (slower) |
| `dirtied` | Blocks changed by the query |
| `written` | Blocks written to disk by the query |
| `temp read/written` | Temp files used (sorts/hashes that spilled to disk). This is a warning sign. |

**Why BUFFERS matter:** Time changes with cache. Block counts do not. Fewer buffers = less work.

## 11.3 Scan types (how PostgreSQL reads a table)

### Seq Scan (Sequential Scan)
Reads the **whole table**, page by page.
```
Seq Scan on customers  (cost=0.00..24000.00 rows=1 width=120)
  Filter: (email = 'x')
```
- ✅ Good when you need most of the table, or the table is small.
- ❌ Bad when you need very few rows from a big table.
- You may see `Parallel Seq Scan` under a `Gather` node. That is several workers sharing the scan.

### Index Scan
Walks the index, then visits the table for each matching row.
```
Index Scan using idx_c_email on customers (cost=0.42..8.44 rows=1 width=120)
  Index Cond: (email = 'user1@example.com')
```
- ✅ Good for **few** rows.
- Each match = random table access, so it gets expensive for many rows.

### Index Only Scan
Answers from the index alone (needs a covering index and a good visibility map).
```
Index Only Scan using idx_orders_cust_incl on orders
  Index Cond: (customer_id = 42)
  Heap Fetches: 0
```
- ✅ The fastest kind.

### Bitmap Index Scan + Bitmap Heap Scan
A middle path for a **medium** number of rows.
1. The **Bitmap Index Scan** collects all matching row locations into a bitmap in memory.
2. The **Bitmap Heap Scan** reads the table pages in **physical order** (less random jumping).
```
Bitmap Heap Scan on customers
  Recheck Cond: (country = 'IN')
  -> Bitmap Index Scan on idx_c_country_status_created
       Index Cond: (country = 'IN')
```
- Can **combine** several indexes using `BitmapAnd` / `BitmapOr`.
- `Recheck Cond` is normal. If the bitmap becomes "lossy" (not enough `work_mem`), it re-checks the condition on each page.

### Summary: which scan, when?

| Rows returned (of table) | Typical choice |
|---|---|
| Very few (< ~1%) | Index Scan / Index Only Scan |
| Some (~1–20%) | Bitmap Heap Scan |
| Many (> ~20%) | Seq Scan |

These are rough numbers. The planner decides using cost, not fixed percentages.

## 11.4 Join algorithms

When you join two tables, PostgreSQL chooses one of three algorithms.

### 11.4.1 Nested Loop

**How it works:** For **each row** in the outer table, look for matches in the inner table.
```
for each row r in outer:
    find rows in inner that match r      (best if this is an index lookup)
```
```
Nested Loop
  -> Index Scan on customers (id = 5)         -- outer: 1 row
  -> Index Scan on orders (customer_id = 5)   -- inner: runs once per outer row
```
- ✅ **Best when the outer side is small** and the inner side has an **index** on the join column.
- ❌ Terrible when both sides are big and there is no index (cost ≈ N × M).
- Only algorithm that works for any join condition (including `<`, `>`, and no condition).
- Watch `loops=` on the inner node: `loops=100000` is a red flag.

### 11.4.2 Hash Join

**How it works:**
1. Build a **hash table** in memory from the **smaller** table (the "build" side).
2. Scan the **bigger** table (the "probe" side) and look up each row in the hash table.
```
Hash Join
  Hash Cond: (o.customer_id = c.id)
  -> Seq Scan on orders o          -- probe side (big)
  -> Hash
       -> Seq Scan on customers c  -- build side (small)
```
- ✅ Great for **large, unsorted** inputs with an **equality** join (`=`).
- ❌ Cannot do `<`/`>` joins.
- Needs memory (`work_mem`). If it doesn't fit: `Batches: N` with N > 1 means it spilled to disk.
- No index needed.

### 11.4.3 Merge Join

**How it works:** Both inputs must be **sorted** on the join key. Then PostgreSQL walks both lists together, like zipping two sorted lists.
```
Merge Join
  Merge Cond: (a.id = b.a_id)
  -> Index Scan on a (already sorted by id)
  -> Index Scan on b (already sorted by a_id)
```
- ✅ Great when inputs are **already sorted** (from an index), or when the result must be sorted anyway.
- Supports `=` joins (and can be used for FULL OUTER JOIN).
- If inputs are not sorted, a `Sort` node is added, which costs extra.

### Quick comparison

| | Nested Loop | Hash Join | Merge Join |
|---|---|---|---|
| Best for | Small outer + indexed inner | Big tables, equality | Pre-sorted big tables |
| Needs index? | Yes, on inner side (ideally) | No | No (but sorted input helps) |
| Needs memory? | No | Yes (`work_mem`) | For sorting |
| Non-equality join | ✅ | ❌ | ❌ |

### Join types vs algorithms
`INNER`, `LEFT`, `RIGHT`, `FULL`, `SEMI` (`EXISTS`/`IN`), `ANTI` (`NOT EXISTS`) are **logical** join types. Any of the three algorithms above can implement them. You might see `Hash Semi Join` or `Hash Anti Join` in plans.

## 11.6 Statistics and ANALYZE

### Why they matter
The planner **guesses** how many rows each step returns. These guesses come from stored statistics. Bad guesses lead to bad plans.

**Sign of a problem:** In `EXPLAIN ANALYZE`, the estimated `rows=` is very different from the actual `rows=` (10× or more).
```
Nested Loop (cost=... rows=5 ...) (actual time=... rows=250000 loops=1)
```
The planner thought 5 rows, got 250,000. It probably picked the wrong join method.

### ANALYZE command

```sql
ANALYZE;                          -- all tables in the database
ANALYZE customers;                -- one table
ANALYZE customers (country, status);   -- specific columns
ANALYZE VERBOSE customers;        -- shows progress
VACUUM ANALYZE customers;         -- vacuum, then analyze
```
- It reads a **sample** of the table (not all rows) and updates the statistics.
- Autovacuum runs auto-analyze in the background. But run `ANALYZE` manually **after bulk loads or big changes**.

### Where statistics live

**Table-level:**
```sql
SELECT relname, reltuples::bigint AS est_rows, relpages
FROM pg_class WHERE relname = 'customers';
```

**Column-level (`pg_stats`):**
```sql
SELECT attname, null_frac, n_distinct, most_common_vals, most_common_freqs,
       histogram_bounds, correlation
FROM pg_stats
WHERE tablename = 'customers' AND attname IN ('country','status','created_at');
```

| Column | Meaning |
|---|---|
| `null_frac` | Fraction of rows that are NULL |
| `n_distinct` | Number of different values. If negative, e.g. `-1`, it means "all values are unique" (−1 = 100% of rows; −0.5 = 50%) |
| `most_common_vals` / `most_common_freqs` | The most frequent values and how often they appear |
| `histogram_bounds` | Boundaries splitting the other values into equal-sized groups |
| `correlation` | How well the physical row order matches the sort order (−1 to 1). High = range scans are cheap (and BRIN works) |

### Improve statistics for a tricky column
```sql
-- Default is 100. Higher = more detailed stats, slower ANALYZE.
ALTER TABLE customers ALTER COLUMN country SET STATISTICS 500;
ANALYZE customers;

-- Change the global default (postgresql.conf or ALTER SYSTEM)
-- default_statistics_target = 100
```

### Extended statistics (columns that depend on each other)
By default the planner thinks columns are **independent**. But `city = 'Paris'` and `country = 'France'` are related. The planner multiplies the chances and underestimates.

```sql
CREATE STATISTICS stat_city_country (dependencies)
ON city, country FROM addresses;

ANALYZE addresses;
```
Other kinds: `ndistinct` (combined distinct counts), `mcv` (combined most-common values, PG 12+).

```sql
CREATE STATISTICS s1 (dependencies, ndistinct, mcv) ON country, status FROM customers;
```

### Planner settings you can test with (testing only!)
```sql
SET enable_seqscan = off;     -- discourage seq scans, to test if an index plan is faster
SET enable_nestloop = off;
SET enable_hashjoin = off;
SET enable_mergejoin = off;
RESET enable_seqscan;
```
> These don't truly "disable" things. They add a huge cost penalty. Use them only to **experiment**. Do not leave them on in production. If forcing a plan helps, find the real cause (stats, missing index, etc.).

Other useful settings:
| Setting | What it does |
|---|---|
| `work_mem` | Memory per sort/hash operation (per node, per query!). Default 4MB. |
| `random_page_cost` | Cost of a random disk read (default 4.0). On SSDs, 1.1 to 1.5 is common. Lower = more index use. |
| `effective_cache_size` | Tells the planner how much memory is available for caching (not an allocation). |
| `max_parallel_workers_per_gather` | How many parallel workers one query can use. |

```sql
SET work_mem = '64MB';   -- only for this session
```

## 11.7 A step-by-step method for reading a plan

1. Run `EXPLAIN (ANALYZE, BUFFERS)`.
2. Look at the **total Execution Time** and **Planning Time**.
3. Find the node with the **largest actual time** (remember: parent time includes child time. Subtract the children to see "self time", and multiply by `loops`).
4. Compare **estimated vs actual rows** at each node. A big gap means stats problems.
5. Look for these **red flags**:
   - `Seq Scan` with a big `Rows Removed by Filter`
   - `loops` in the thousands or millions on an inner node
   - `Sort Method: external merge  Disk`
   - `Hash` with `Batches > 1`
   - `Heap Fetches` high on an Index Only Scan
   - Many `read` buffers or any `temp` buffers
6. Fix, re-run, compare.

## 11.8 Reading 5 query plans (sample plans with explanations)

Use the `customers` table from Day 10. Let's also create an `orders` table for join examples:

```sql
CREATE TABLE orders AS
SELECT
  g AS id,
  1 + (random()*999999)::int AS customer_id,
  (DATE '2025-01-01' + (random()*700)::int) AS order_date,
  round((random()*500)::numeric,2) AS amount,
  (ARRAY['new','paid','shipped','cancelled'])[1+(random()*3)::int] AS status
FROM generate_series(1, 2000000) g;

ALTER TABLE orders ADD PRIMARY KEY (id);
ANALYZE orders;
```
(No index on `customer_id` yet, on purpose.)

---

### Plan 1: Simple primary-key lookup

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM customers WHERE id = 500000;
```
```
Index Scan using customers_pkey on customers  (cost=0.42..8.44 rows=1 width=130) (actual time=0.020..0.021 rows=1 loops=1)
  Index Cond: (id = 500000)
  Buffers: shared hit=4
Planning Time: 0.080 ms
Execution Time: 0.040 ms
```
**Read it:** `Index Scan` on the primary key. 1 row estimated, 1 row actual. 4 buffers (3 index levels + 1 table page). ✅ Perfect. Nothing to fix.

---

### Plan 2: Seq Scan with a big filter loss

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 12345;   -- no index on customer_id
```
```
Gather  (cost=1000.00..28000.00 rows=2 width=30) (actual time=40.1..95.3 rows=2 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  Buffers: shared hit=... read=14000
  -> Parallel Seq Scan on orders  (cost=0.00..27000.00 rows=1 width=30) (actual time=60.2..90.0 rows=1 loops=3)
       Filter: (customer_id = 12345)
       Rows Removed by Filter: 666666
Execution Time: 96.0 ms
```
**Read it:** It reads the **whole table** (2M rows) to return 2 rows. `Rows Removed by Filter: 666666` per worker is the red flag.
**Fix:** `CREATE INDEX idx_orders_customer ON orders (customer_id);`. After this you will see an `Index Scan` or `Bitmap Heap Scan` with time under 1 ms.

> **Foreign keys do NOT create indexes automatically in PostgreSQL** (on the referencing side). Add them yourself for join columns.

---

### Plan 3: Join: Hash Join

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.country, count(*), sum(o.amount)
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.order_date >= '2026-01-01'
GROUP BY c.country;
```
```
HashAggregate  (actual time=900..900 rows=8 loops=1)
  Group Key: c.country
  -> Hash Join  (actual time=250..750 rows=1000000 loops=1)
       Hash Cond: (o.customer_id = c.id)
       -> Seq Scan on orders o  (actual time=0.0..200 rows=1000000 loops=1)
            Filter: (order_date >= '2026-01-01')
            Rows Removed by Filter: 1000000
       -> Hash  (actual time=240..240 rows=1000000 loops=1)
            Buckets: 1048576  Batches: 4  Memory Usage: 40000kB
            -> Seq Scan on customers c  (actual time=0.0..90 rows=1000000 loops=1)
```
**Read it:**
- A big join with a large share of rows → `Hash Join` is the right choice.
- `Batches: 4` means the hash table did not fit in `work_mem` and spilled to disk. Try `SET work_mem = '128MB';` and see `Batches: 1`.
- Here a `Seq Scan` is fine because half of the table matches.

---

### Plan 4: Nested Loop that explodes (bad estimate)

```sql
EXPLAIN (ANALYZE)
SELECT * FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE c.country = 'IN';
```
Imagine the plan shows:
```
Nested Loop  (cost=0.43..5000.00 rows=20 width=...) (actual time=0.1..45000 rows=250000 loops=1)
  -> Seq Scan on customers c  (rows=125000 actual)
  -> Seq Scan on orders o  (actual time=... rows=2 loops=125000)
       Filter: (customer_id = c.id)
       Rows Removed by Filter: 1999998
```
**Read it:**
- The inner node ran `loops=125000` times, and each time it scanned the whole `orders` table. That is the "N × M" disaster.
- The planner **estimated** 20 rows but got 250,000, so it chose a nested loop. This means stats are wrong or there is no index.
- **Fix:** `CREATE INDEX ON orders (customer_id); ANALYZE orders;`. Now the inner side becomes an index scan, or the planner moves to a Hash Join.

---

### Plan 5: Sort that spills to disk

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY amount DESC LIMIT 10;
```
Possible plan (without index):
```
Limit  (actual time=500..500 rows=10 loops=1)
  -> Gather Merge ...
       -> Sort  (actual time=480..480 rows=10 loops=3)
            Sort Key: amount DESC
            Sort Method: top-N heapsort  Memory: 26kB
            -> Parallel Seq Scan on orders (actual time=0.0..250 rows=666667 loops=3)
```
**Read it:**
- `top-N heapsort` is smart: because of `LIMIT 10`, PostgreSQL keeps only the top 10 in memory. ✅ Fine, but it still reads the whole table.
- With an index `CREATE INDEX ON orders (amount DESC);`, this becomes `Limit → Index Scan` and finishes in < 1 ms.

If you remove the `LIMIT`: `ORDER BY amount DESC` on 2M rows could show `Sort Method: external merge  Disk: 60000kB`, meaning it spilled to disk. Fix by raising `work_mem` or adding an index.

## 11.9 Fixing 2 slow queries (full walk-throughs)

### Slow Query #1: "Case-insensitive search is slow"

**Problem:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM customers WHERE lower(email) = 'user777777@example.com';
```
```
Seq Scan on customers (actual time=0.0..250 rows=1 loops=1)
  Filter: (lower(email) = 'user777777@example.com')
  Rows Removed by Filter: 999999
Execution Time: 260 ms
```
**Diagnosis:** An index on `email` exists, but the query uses `lower(email)`, so the index can't be used.

**Fix:**
```sql
CREATE INDEX idx_c_lower_email ON customers (lower(email));
ANALYZE customers;
```
**After:**
```
Index Scan using idx_c_lower_email on customers (actual time=0.03..0.03 rows=1 loops=1)
Execution Time: 0.06 ms
```
**Lesson:** Functions on columns block normal indexes. Use an expression index (or rewrite the query so the column is "bare").

---

### Slow Query #2: "Join + sort + pagination is slow"

**Problem:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT o.id, o.amount, o.order_date
FROM orders o
WHERE o.customer_id = 12345
ORDER BY o.order_date DESC
LIMIT 10;
```
Without any index on `customer_id`:
```
Limit
  -> Sort (Sort Key: order_date DESC)
       -> Seq Scan on orders (Filter: customer_id = 12345, Rows Removed by Filter: 1999998)
Execution Time: 180 ms
```
**Fix:** A composite index that matches **filter + sort**:
```sql
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date DESC) INCLUDE (amount);
ANALYZE orders;
```
**After:**
```
Limit
  -> Index Only Scan using idx_orders_cust_date on orders
       Index Cond: (customer_id = 12345)
       Heap Fetches: 0
Execution Time: 0.05 ms
```
No `Sort` node. The index returns rows already in order. `INCLUDE (amount)` makes it an index-only scan.

**Bonus: slow deep pagination with `OFFSET`:**
```sql
-- Slow for big offsets (must read and throw away 100000 rows)
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 100000;

-- Fast: keyset pagination ("seek" method)
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
```

### A general "slow query fix" checklist

1. Run `EXPLAIN (ANALYZE, BUFFERS)`.
2. Is estimated rows far from actual rows? → `ANALYZE`, raise statistics target, add extended statistics.
3. Seq Scan on a big table with few rows returned? → add an index.
4. Index exists but not used? → function/cast on the column, wrong column order, type mismatch, leading wildcard.
5. Sort spills to disk? → increase `work_mem` (carefully), or add an index that provides the order.
6. Hash batches > 1? → increase `work_mem`.
7. Nested loop with huge `loops`? → index the inner join column, check estimates.
8. Return fewer columns: avoid `SELECT *`.
9. Still slow? Rewrite the query (replace correlated subqueries, use `EXISTS` instead of `IN` with big lists, avoid `OR` across different columns, use `UNION ALL`).

**`pg_stat_statements` extension** (the most useful tool):

```sql
-- postgresql.conf: shared_preload_libraries = 'pg_stat_statements'   (restart needed)

```

# Day 12: VACUUM, Bloat and Partitioning

## 12.1 MVCC: why VACUUM exists

PostgreSQL uses **MVCC (Multi-Version Concurrency Control)**. Readers do not block writers, and writers do not block readers. How? **It never overwrites a row.**

- `UPDATE` = mark the old row version as "dead" + insert a **new version**.
- `DELETE` = mark the row as "dead" (it is not physically removed).

The old versions are kept because other running transactions may still need to see them.

### Dead tuples
A **tuple** = a row version. A **dead tuple** = an old version that **no transaction can see anymore**. It still takes space.

```
Before update:   [ id=1, balance=100 ]
After update:    [ id=1, balance=100 ] (dead)   [ id=1, balance=150 ] (live)
```

If dead tuples are never cleaned, the table grows bigger and bigger. This is **bloat**.

### Bloat
Bloat = wasted space in tables and indexes (dead tuples and empty gaps). Effects:
- Bigger tables/indexes → more disk I/O → slower queries.
- More memory used for cache.
- Seq scans read useless pages.

---

## 12.2 VACUUM

### What VACUUM does
1. Finds **dead tuples** and marks their space as **reusable** (for new rows in the same table).
2. Updates the **visibility map** (helps Index-Only Scans and future vacuums).
3. Updates the **free space map**.
4. **Freezes** old row versions to prevent transaction ID wraparound (see below).
5. Does **not** usually shrink the file on disk (only frees empty pages at the very end).
6. Does **not** block normal reads/writes (it takes a light lock).

### Syntax

```sql
VACUUM;                               -- all tables
VACUUM customers;                     -- one table
VACUUM (VERBOSE) customers;           -- show details
VACUUM (ANALYZE) customers;           -- vacuum + update statistics
VACUUM (VERBOSE, ANALYZE) customers;
VACUUM (FREEZE) customers;            -- aggressively freeze old rows
VACUUM (PARALLEL 4) customers;        -- parallel index vacuuming (PG 13+)
VACUUM (INDEX_CLEANUP OFF) customers; -- skip indexes (emergency use)
VACUUM (FULL) customers;              -- REWRITES the table (see below)
```

### VACUUM FULL: use with care
- Rewrites the whole table into a **new file**, compacts it, and returns space to the operating system.
- Takes an **`ACCESS EXCLUSIVE` lock**: **nobody can read or write** the table until it finishes.
- Needs extra disk space (a full copy).
- Use only in a maintenance window, or use the extension **`pg_repack`** (online, far less blocking) instead.

| | `VACUUM` | `VACUUM FULL` |
|---|---|---|
| Blocks reads/writes | No | **Yes** |
| Returns space to OS | Rarely | Yes |
| Reuses space inside table | Yes | Yes (rewrites compactly) |
| Speed | Faster | Slow |
| Daily use | ✅ | ❌ |

### Demo: see dead tuples appear

```sql
CREATE TABLE vac_demo (id int PRIMARY KEY, val int);
INSERT INTO vac_demo SELECT g, 0 FROM generate_series(1, 100000) g;

-- Disable autovacuum on this table so you can watch
ALTER TABLE vac_demo SET (autovacuum_enabled = false);

-- Create dead tuples
UPDATE vac_demo SET val = val + 1;
UPDATE vac_demo SET val = val + 1;

SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'vac_demo';
SELECT pg_size_pretty(pg_relation_size('vac_demo'));   -- bigger than expected!

VACUUM (VERBOSE) vac_demo;

SELECT n_live_tup, n_dead_tup FROM pg_stat_user_tables WHERE relname = 'vac_demo';
SELECT pg_size_pretty(pg_relation_size('vac_demo'));   -- same size, but space is now reusable

VACUUM FULL vac_demo;
SELECT pg_size_pretty(pg_relation_size('vac_demo'));   -- smaller now

ALTER TABLE vac_demo SET (autovacuum_enabled = true);
```
(The stats views update a short moment later, so wait a second or two before checking them.)

## 12.3 Autovacuum

### What it is
A background process that **automatically** runs `VACUUM` and `ANALYZE` when enough rows have changed. **Keep it ON.** Never turn it off globally.

### When does it start?

For **vacuum**:
```
vacuum threshold = autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × number_of_rows
                 =            50              +           0.2                   × reltuples
```
For a table with **1,000,000 rows**: 50 + 0.2 × 1,000,000 = **200,050 dead rows** before autovacuum starts. That is a lot! For **100 million rows** it waits for about 20 million dead rows.

For **analyze**:
```
analyze threshold = autovacuum_analyze_threshold (50) + autovacuum_analyze_scale_factor (0.1) × reltuples
```

There is also an **insert-based trigger** (PG 13+): `autovacuum_vacuum_insert_threshold` (1000) and `autovacuum_vacuum_insert_scale_factor` (0.2), so insert-only tables still get vacuumed (for freezing and the visibility map).

### Main settings

| Setting | Default | Meaning |
|---|---|---|
| `autovacuum` | on | Master switch |
| `autovacuum_naptime` | 1min | How often the launcher checks databases |
| `autovacuum_max_workers` | 3 | Max parallel autovacuum workers (restart needed) |
| `autovacuum_vacuum_threshold` | 50 | Base number of dead rows |
| `autovacuum_vacuum_scale_factor` | 0.2 | Fraction of table size |
| `autovacuum_analyze_threshold` | 50 | Base number of changed rows |
| `autovacuum_analyze_scale_factor` | 0.1 | Fraction of table size |
| `autovacuum_vacuum_cost_delay` | 2ms | Pause between work chunks (throttling) |
| `autovacuum_vacuum_cost_limit` | -1 (uses `vacuum_cost_limit` = 200) | How much work before pausing |
| `autovacuum_freeze_max_age` | 200 million | Forces anti-wraparound vacuum |

### Tuning: per-table settings (the best approach)

Big, busy tables need a **smaller scale factor**:
```sql
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.01,    -- 1% instead of 20%
  autovacuum_vacuum_threshold    = 1000,
  autovacuum_analyze_scale_factor = 0.02
);

-- See the settings on a table
SELECT relname, reloptions FROM pg_class WHERE relname = 'orders';

-- Reset them
ALTER TABLE orders RESET (autovacuum_vacuum_scale_factor);
```

### Tuning: global settings
```sql
ALTER SYSTEM SET autovacuum_vacuum_cost_limit = 2000;   -- let it work faster
ALTER SYSTEM SET autovacuum_vacuum_scale_factor = 0.05;
SELECT pg_reload_conf();
```
(`autovacuum_max_workers` needs a server restart.)

**Tuning guide:**

| Symptom | Likely action |
|---|---|
| Dead tuples keep growing on a big table | Lower `scale_factor` for that table |
| Autovacuum is too slow, always running | Raise `autovacuum_vacuum_cost_limit` (and/or lower `cost_delay`), more `max_workers` |
| Autovacuum hurts query performance | Lower the cost limit, run in quiet hours (carefully) |
| Stats are stale after batch loads | Run `ANALYZE` manually after the load |
| Many big tables, few workers | Increase `autovacuum_max_workers` (and remember the cost limit is shared between workers) |

### Why autovacuum may fail to clean (very common problem!)
VACUUM can only remove dead tuples that **no transaction might still need**. These block it:
1. **Long-running transactions** (or sessions stuck as `idle in transaction`).
2. **Abandoned replication slots.**
3. **Old prepared transactions.**
4. **Standby with `hot_standby_feedback`** and long queries.

Find long transactions:
```sql
SELECT pid, usename, state, now() - xact_start AS xact_age, left(query, 60) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 10;
```
Protect yourself:
```sql
ALTER SYSTEM SET idle_in_transaction_session_timeout = '10min';
```

### Transaction ID wraparound (important to know)
Each transaction gets a 32-bit ID. IDs eventually wrap around. VACUUM **freezes** old rows so they stay visible forever. If it is not done, PostgreSQL will eventually **stop accepting writes** to protect the data. Monitor:
```sql
SELECT datname, age(datfrozenxid) AS xid_age FROM pg_database ORDER BY xid_age DESC;
```
Worry when the age gets close to ~1 billion+ (the hard limit is ~2 billion). The `autovacuum_freeze_max_age` (200M) trigger normally keeps it far away.

### Reduce bloat from updates: HOT updates and fillfactor
**HOT (Heap-Only Tuple) update:** If you update a column that is **not indexed**, and there is free space in the same page, PostgreSQL can skip updating the indexes. That is faster and creates less bloat.

```sql
ALTER TABLE orders SET (fillfactor = 90);   -- leave 10% free space in each page
```
(Applies to new pages, or after a rewrite.) Good for tables with many updates. Do not use on append-only tables.

## 12.4 The `pg_stat_*` views

PostgreSQL collects statistics about activity. These views are your **dashboard**.

### Overview

| View | What it shows |
|---|---|
| `pg_stat_activity` | Current sessions and queries (find long or stuck queries) |
| `pg_stat_user_tables` | Per-table stats: scans, rows inserted/updated/deleted, dead tuples, last vacuum |
| `pg_stat_user_indexes` | Per-index usage (`idx_scan`) |
| `pg_statio_user_tables` / `pg_statio_user_indexes` | Cache hit/disk read counts |
| `pg_stat_database` | Per-database totals (commits, rollbacks, cache hits, deadlocks) |
| `pg_stat_bgwriter` / `pg_stat_checkpointer` | Background writer and checkpoint activity (the checkpointer view is new in PG 17) |
| `pg_stat_progress_vacuum` | Live progress of running VACUUMs |
| `pg_stat_progress_create_index` | Live progress of index builds |
| `pg_stat_statements` | Query-level statistics (extension) |
| `pg_locks` | Current locks |
| `pg_stat_replication` | Replication status |

### Useful queries

**1) Tables with the most dead tuples:**
```sql
SELECT relname,
       n_live_tup,
       n_dead_tup,
       round(100.0 * n_dead_tup / nullif(n_live_tup + n_dead_tup, 0), 2) AS dead_pct,
       last_vacuum, last_autovacuum, last_analyze, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC
LIMIT 10;
```
Rule of thumb: dead_pct above ~10–20% on a big table deserves attention.

**2) Tables that are read by seq scan a lot (candidates for indexes):**
```sql
SELECT relname, seq_scan, seq_tup_read, idx_scan,
       round(seq_tup_read::numeric / nullif(seq_scan,0)) AS avg_rows_per_seq_scan
FROM pg_stat_user_tables
ORDER BY seq_tup_read DESC
LIMIT 10;
```

**3) Table activity and HOT updates:**
```sql
SELECT relname, n_tup_ins, n_tup_upd, n_tup_hot_upd, n_tup_del
FROM pg_stat_user_tables
ORDER BY n_tup_upd DESC LIMIT 10;
```
Low `n_tup_hot_upd` compared to `n_tup_upd` means updates are touching indexed columns or pages are full.

**4) Cache hit ratio (should be above ~99% for OLTP):**
```sql
SELECT sum(heap_blks_hit) * 100.0 / nullif(sum(heap_blks_hit + heap_blks_read), 0) AS table_hit_pct
FROM pg_statio_user_tables;
```

**5) Running vacuum progress:**
```sql
SELECT * FROM pg_stat_progress_vacuum;
```

**6) What is running right now?**
```sql
SELECT pid, state, now() - query_start AS runtime, wait_event_type, wait_event, left(query, 80)
FROM pg_stat_activity
WHERE state <> 'idle'
ORDER BY query_start;
```
Stop a query: `SELECT pg_cancel_backend(pid);` (polite). Kill a connection: `SELECT pg_terminate_backend(pid);` (hard).

**7) Reset statistics (careful):**
```sql
SELECT pg_stat_reset();   -- current database
```

### Measuring bloat accurately: `pgstattuple`
```sql
CREATE EXTENSION IF NOT EXISTS pgstattuple;

SELECT * FROM pgstattuple('orders');
-- look at: dead_tuple_percent, free_percent

SELECT * FROM pgstatindex('idx_orders_customer');
-- look at: avg_leaf_density (low = bloated), leaf_fragmentation
```
It reads the whole table, so it is heavy. For a quick approximation, use `pgstattuple_approx('orders')`.

### Fixing bloat: options

| Situation | Fix |
|---|---|
| Normal level of dead rows | Let autovacuum handle it |
| Autovacuum behind | Tune it (see above), run a manual `VACUUM` |
| Heavily bloated table | `pg_repack` (online) or `VACUUM FULL` (offline, locks table) |
| Bloated index | `REINDEX INDEX CONCURRENTLY idx_name;` |
| Old data keeps accumulating | **Partition** and drop old partitions (instant, no vacuum needed) |

## 12.5 Table partitioning

### What it is
Splitting **one big logical table** into **many smaller physical tables** (called **partitions**). You still query the main table (the **parent**), and PostgreSQL routes data to the right partition.

```
orders  (parent, holds no data itself)
  ├── orders_2026_01   (January)
  ├── orders_2026_02   (February)
  ├── ...
  └── orders_2026_12   (December)
```

### Why partition?

1. **Partition pruning:** If the query filters by the partition key, PostgreSQL scans **only the needed partitions**.
2. **Fast data removal:** Drop or detach an old partition (`DROP TABLE orders_2024_01`) instead of `DELETE` + VACUUM of millions of rows.
3. **Faster maintenance:** `VACUUM`, `REINDEX`, and backups work on smaller pieces. Autovacuum works per partition.
4. **Smaller indexes** per partition fit in memory better.
5. **Data tiering:** Put old partitions on cheaper storage (tablespaces).

### When to use / not use

✅ Use when:
- The table is **very large** (rule of thumb: bigger than the memory of your server, or many tens of GB).
- Data has a natural key such as **time** and old data is archived/dropped.
- Most queries filter on the partition key.

❌ Don't use when:
- The table is small or medium. Partitioning adds complexity and does not help.
- Queries rarely filter by the partition key (they will scan all partitions: slower!).
- You expect **thousands** of partitions (planning gets slow). Hundreds is OK.

### Partition types

| Type | How rows are assigned | Typical use |
|---|---|---|
| **RANGE** | By a range of values | Dates (per month/day), numeric ID ranges |
| **LIST** | By exact list of values | Country, region, status, tenant type |
| **HASH** | By hash of a value: `MODULUS` / `REMAINDER` | Spread data evenly when there is no natural range (e.g., `customer_id`) |

### Syntax

**RANGE:**
```sql
CREATE TABLE measurements (
  id        bigserial,
  logged_at timestamptz NOT NULL,
  value     numeric,
  PRIMARY KEY (id, logged_at)
) PARTITION BY RANGE (logged_at);

CREATE TABLE measurements_2026_10 PARTITION OF measurements
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');   -- FROM is inclusive, TO is EXCLUSIVE
```

**LIST:**
```sql
CREATE TABLE sales (
  id      bigserial,
  region  text NOT NULL,
  amount  numeric,
  PRIMARY KEY (id, region)
) PARTITION BY LIST (region);

CREATE TABLE sales_asia   PARTITION OF sales FOR VALUES IN ('IN','JP','CN');
CREATE TABLE sales_europe PARTITION OF sales FOR VALUES IN ('DE','FR','UK');
CREATE TABLE sales_other  PARTITION OF sales DEFAULT;   -- catches everything else
```

**HASH:**
```sql
CREATE TABLE events (
  id          bigserial,
  customer_id bigint NOT NULL,
  payload     jsonb,
  PRIMARY KEY (id, customer_id)
) PARTITION BY HASH (customer_id);

CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0);
CREATE TABLE events_p1 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 1);
CREATE TABLE events_p2 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 2);
CREATE TABLE events_p3 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 3);
```
For `HASH`, you must create **all** remainders (0 to MODULUS−1), or inserts for the missing ones fail.

### Important rules and limits

1. **Primary key / unique constraints must include the partition key.** (That is why `PRIMARY KEY (id, order_date)`.) PostgreSQL cannot enforce uniqueness across partitions otherwise.
2. The parent table **stores no rows**. Rows live in partitions.
3. If no partition matches a row's key (and there's no `DEFAULT` partition), the insert **fails** with "no partition of relation found for row".
4. Range bounds: `FROM` inclusive, `TO` **exclusive**. So `FROM ('2026-01-01') TO ('2026-02-01')` covers all of January.
5. Indexes created on the parent are created on **every partition** automatically (including future ones).
6. Updating the partition key can **move** the row to another partition (works, but is costly).
7. Foreign keys **to** partitioned tables are supported (PG 12+). Foreign keys **from** partitioned tables are supported (PG 11+).
8. Create a `DEFAULT` partition as a safety net, but be careful: adding a new partition later requires scanning the default one for conflicting rows.
9. Pick a partition key that your queries filter on **most often**.

### Sub-partitioning (multi-level)
```sql
CREATE TABLE orders_2026_01 PARTITION OF orders
  FOR VALUES FROM ('2026-01-01') TO ('2026-02-01')
  PARTITION BY HASH (customer_id);
```
Use it rarely. It makes things more complex.

### Managing partitions

```sql
-- Add a new partition
CREATE TABLE orders_2027_01 PARTITION OF orders
  FOR VALUES FROM ('2027-01-01') TO ('2027-02-01');

-- Remove old data quickly (data is KEPT as a standalone table)
ALTER TABLE orders DETACH PARTITION orders_2026_01;
ALTER TABLE orders DETACH PARTITION orders_2026_01 CONCURRENTLY;   -- PG 14+, less blocking

-- Then archive or drop it
DROP TABLE orders_2026_01;

-- Attach an existing table as a partition
-- (Add a matching CHECK constraint first so PostgreSQL can skip the full validation scan)
ALTER TABLE orders_2027_02 ADD CONSTRAINT chk_2027_02
  CHECK (order_date >= '2027-02-01' AND order_date < '2027-03-01');
ALTER TABLE orders ATTACH PARTITION orders_2027_02
  FOR VALUES FROM ('2027-02-01') TO ('2027-03-01');
```

**List partitions of a table:**
```sql
SELECT inhrelid::regclass AS partition,
       pg_get_expr(c.relpartbound, c.oid) AS bounds
FROM pg_inherits i
JOIN pg_class c ON c.oid = i.inhrelid
WHERE i.inhparent = 'orders'::regclass;
```
or in `psql`: `\d+ orders`

### Partition pruning check
```sql
EXPLAIN SELECT * FROM orders WHERE order_date = '2026-03-15';
```
You should see **only** `orders_2026_03` in the plan. If you see all partitions, the filter is not on the key, or it uses a function on the key (`WHERE date_trunc('month', order_date) = ...` does not prune; use a plain range instead).

The settings `enable_partition_pruning` (default `on`) controls this.

### Partitioning is not a replacement for indexes
Inside each partition you still need indexes for non-key filters (e.g., `customer_id`).

## 12.6 Hands-on (Day 12): Partition an `orders` table by month

We will build a partitioned table for the year 2026, load 1M rows, and compare against a normal table.

### Step 1: Create the partitioned parent

```sql
DROP TABLE IF EXISTS orders_part CASCADE;

CREATE TABLE orders_part (
  id          bigserial,
  customer_id bigint        NOT NULL,
  order_date  date          NOT NULL,
  amount      numeric(10,2) NOT NULL,
  status      text          NOT NULL,
  PRIMARY KEY (id, order_date)          -- partition key included!
) PARTITION BY RANGE (order_date);
```

### Step 2: Create 12 monthly partitions (with a loop)

```sql
DO $$
DECLARE
  m date;
BEGIN
  FOR m IN SELECT generate_series(DATE '2026-01-01', DATE '2026-12-01', INTERVAL '1 month')::date
  LOOP
    EXECUTE format(
      'CREATE TABLE %I PARTITION OF orders_part FOR VALUES FROM (%L) TO (%L)',
      'orders_part_' || to_char(m, 'YYYY_MM'),
      m,
      (m + INTERVAL '1 month')::date
    );
  END LOOP;
END $$;

-- Safety net for unexpected dates
CREATE TABLE orders_part_default PARTITION OF orders_part DEFAULT;
```

### Step 3: Create indexes on the parent (they cascade)

```sql
CREATE INDEX idx_orders_part_customer ON orders_part (customer_id);
CREATE INDEX idx_orders_part_status_date ON orders_part (status, order_date);
```

### Step 4: Load 1M rows spread across 2026

```sql
INSERT INTO orders_part (customer_id, order_date, amount, status)
SELECT
  1 + (random()*999999)::int,
  DATE '2026-01-01' + (random()*364)::int,
  round((random()*500)::numeric, 2),
  (ARRAY['new','paid','shipped','cancelled'])[1 + (random()*3)::int]
FROM generate_series(1, 1000000);

ANALYZE orders_part;
```

### Step 5: Check the data landed in the right partitions

```sql
SELECT tableoid::regclass AS partition, count(*)
FROM orders_part
GROUP BY 1
ORDER BY 1;
```
`tableoid::regclass` tells you which physical table each row lives in. You should see about 80–90K rows per month, and **0 rows in the default partition**.

### Step 6: See partition pruning in action

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), sum(amount)
FROM orders_part
WHERE order_date >= '2026-03-01' AND order_date < '2026-04-01';
```
Expected: only **`orders_part_2026_03`** appears in the plan.

Now compare with pruning off:
```sql
SET enable_partition_pruning = off;
EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), sum(amount)
FROM orders_part
WHERE order_date >= '2026-03-01' AND order_date < '2026-04-01';
RESET enable_partition_pruning;
```
You will see all 13 partitions scanned. Compare times and buffers.

And a **bad** query (no partition key filter):
```sql
EXPLAIN SELECT * FROM orders_part WHERE customer_id = 12345;
```
This touches **every** partition (and each index). It works, but it is slower than on a single table. Lesson: choose the partition key wisely.

### Step 7: Compare with a normal (unpartitioned) table

```sql
CREATE TABLE orders_plain AS SELECT id, customer_id, order_date, amount, status FROM orders_part;
CREATE INDEX ON orders_plain (order_date);
ANALYZE orders_plain;

EXPLAIN (ANALYZE, BUFFERS)
SELECT count(*), sum(amount) FROM orders_plain
WHERE order_date >= '2026-03-01' AND order_date < '2026-04-01';
```
For a 1M-row table, the difference may be small because the B-tree on `order_date` is already good. Partitioning shines with **huge** tables and **maintenance** tasks, as the next step shows.

### Step 8: Experience the maintenance benefit (drop old data)

```sql
-- Plain table: slow, creates dead tuples, needs VACUUM
BEGIN;
EXPLAIN ANALYZE DELETE FROM orders_plain WHERE order_date < '2026-02-01';
ROLLBACK;

-- Partitioned table: instant
BEGIN;
ALTER TABLE orders_part DETACH PARTITION orders_part_2026_01;
DROP TABLE orders_part_2026_01;
ROLLBACK;   -- you can roll back DDL in PostgreSQL. Use COMMIT for real.
```
The `DETACH` + `DROP` takes milliseconds. It creates **no dead tuples** and needs **no vacuum**.

### Step 9: Test the "no partition found" error

```sql
DROP TABLE orders_part_default;     -- remove the safety net for the test
INSERT INTO orders_part (customer_id, order_date, amount, status)
VALUES (1, '2030-01-01', 10, 'new');
-- ERROR: no partition of relation "orders_part" found for row
```
Add the next-year partition, or re-create the `DEFAULT` partition.

### Step 10: Plan for the future
Partitions must exist **before** data arrives. Automate this:
- A scheduled job (`cron` / `pg_cron`) that creates next month's partition in advance.
- Or the extension **`pg_partman`**, which creates and drops partitions automatically.

### Step 11: Check autovacuum per partition
```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables
WHERE relname LIKE 'orders_part_%'
ORDER BY relname;
```
Notice that autovacuum works on each partition separately. Old, no-longer-updated partitions need almost no vacuuming.

> Note: Autovacuum does **not** run `ANALYZE` on the **parent** partitioned table itself. Run `ANALYZE orders_part;` manually now and then for good parent-level statistics.

# Final Cheat Sheet

## Index decision guide

| I need to speed up… | Use |
|---|---|
| `WHERE col = value`, `<`, `>`, `BETWEEN`, `ORDER BY` | **B-tree** |
| Only `=` on very long values | Hash (or just B-tree) |
| `WHERE tags @> ARRAY[...]` | **GIN** |
| `WHERE jsonb_col @> '{...}'` | **GIN** (`jsonb_path_ops` if only `@>`) |
| Full-text search `@@` | **GIN** on `to_tsvector(...)` |
| `LIKE '%text%'`, `ILIKE` | **GIN + pg_trgm** |
| `LIKE 'text%'` | B-tree with `text_pattern_ops` |
| Nearest neighbor, geometry, range overlap | **GiST** |
| "No overlapping bookings" | **GiST** exclusion constraint |
| Huge append-only table, time column | **BRIN** |
| Filter on 2+ columns together | **Composite** B-tree (equality columns first) |
| Only a small subset of rows matter | **Partial** index |
| Avoid table lookups for hot queries | **Covering** index (`INCLUDE`) |
| Query uses `lower(col)` or other function | **Expression** index |

## Performance commands

```sql
EXPLAIN (ANALYZE, BUFFERS) <query>;     -- inside BEGIN/ROLLBACK for DML!
ANALYZE table_name;
VACUUM (VERBOSE, ANALYZE) table_name;
CREATE INDEX CONCURRENTLY ...;
REINDEX INDEX CONCURRENTLY ...;
SELECT pg_size_pretty(pg_total_relation_size('table_name'));
```

## Plan red flags

| You see | Meaning | Typical fix |
|---|---|---|
| Seq Scan + huge `Rows Removed by Filter` | Missing/unusable index | Add the right index |
| Estimated rows ≫≪ actual rows | Bad statistics | `ANALYZE`, raise stats target, `CREATE STATISTICS` |
| Inner node with huge `loops` | Nested Loop explosion | Index the join column, fix estimates |
| `Sort Method: external merge Disk` | Sort spilled | Raise `work_mem`, add an index for the order |
| Hash `Batches: > 1` | Hash spilled | Raise `work_mem` |
| `Heap Fetches` large on Index Only Scan | Visibility map outdated | `VACUUM` |
| `temp read/written` in Buffers | Using disk temp files | Raise `work_mem`, rewrite the query |

## Vacuum and bloat quick rules

1. Keep autovacuum **ON**.
2. For big, busy tables, **lower** the per-table `autovacuum_vacuum_scale_factor`.
3. Hunt long-running and `idle in transaction` sessions.
4. Avoid `VACUUM FULL` on live tables. Use `pg_repack`.
5. Monitor `n_dead_tup` and `age(datfrozenxid)`.

## Partitioning quick rules

1. Only for **big** tables.
2. Partition key = the column most queries filter on (often a date).
3. PK/unique must **include** the partition key.
4. Always filter on the partition key to get pruning.
5. Create future partitions **ahead of time**. Keep a `DEFAULT` partition as a safety net.
6. Keep the number of partitions reasonable (tens to hundreds).

---

**You now have the full performance toolkit:** *indexes* make reads fast, *EXPLAIN* tells you what is really happening, *VACUUM* keeps the storage healthy, and *partitioning* keeps huge tables manageable. Always **measure first, change one thing, and measure again.**
